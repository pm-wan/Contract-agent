# 审查模式与工作流

## 1. 共同准备

先形成 `review_context`：

- 模式、审查用途和请求范围；
- 我方语义角色，不只记录“甲方/乙方”；
- 合同类型、法域和企业主体；
- 每份材料的 `document_id`、文件名、版本、日期、哈希、解析状态；
- 主协议、订单、SOW、技术规格、验收标准、DPA、报价及修订之间的关系；
- 适用规则包、企业立场和规范依据版本；
- 已知缺失材料、解析告警和权限限制。

合同金额没有出现在主协议时，检查订单或事实快照。仍然缺失则将依赖金额的槽位置为 `needs_material`；不得虚构金额，也不得默认路由至某个具名审批人。

## 2. quick_triage

快速分诊只回答四件事：材料是否可审、我方角色与合同结构、是否存在明显关键阻断、完整审查应加载哪些规则包。至少输出材料缺口、解析告警、候选关键问题、规则包选择和下一步。

分诊不是完整审查，不得输出“未发现其他风险”“可以签署”或完整覆盖率。

## 3. full_review

### 3.1 材料和结构定位

1. 建立材料清单，判断主协议、附件和修订是否齐全。
2. 建立定义、正文、附件、引用文件和签署页索引。
3. 记录页缺失、乱码、扫描质量、表格错位、加密和截断等解析告警。
4. 确认我方角色、合同类型和法域；不符合技能范围时停止确定性审查并转人工。

### 3.2 逐项检查

按审计计划执行；无审计计划时根据 `rule-catalog.md` 加载核心合同包以及由合同结构触发的专项包。每项规则分别形成：

- 适用性及依据；
- 槽位状态和值；
- 合同事实与精确证据；
- 企业立场偏离；
- 法律效力疑点及已核验规范依据；
- 风险机制和实际影响；
- 最小修订建议；
- 补材料、法务复核或审批任务。

同一条款可以支持多个规则，但每个结果保留自身判断与证据引用。不得把关键词命中直接当成结论。

### 3.3 联动复核

至少检查：

- 定义是否放大正文义务；
- 交叉引用是否错误或将义务扩展到缺失附件；
- 付款是否先于可验证验收；
- 验收、质保、违约和解除救济能否闭环；
- 责任上限与赔偿、违约金、知识产权、保密及例外如何互动；
- 终止后退款、数据/材料返还、成果交付、许可和保密存续是否一致；
- 主协议、订单、SOW 和附件的优先级是否明确。

联动发现引用原始规则结果，不复制或篡改基础事实。

### 3.4 汇总

先按固定门禁计算覆盖和限制，再生成人类可读摘要。若任一关键规则为 `needs_material`、`conflicted`、`undetermined` 或 `human_review`，摘要必须显式说明不得自动通过。

## 4. focused_check

只执行用户指定主题对应的规则，并列出未审范围。若指定主题依赖另一规则的事实，可读取该事实或产生依赖槽位，但不得暗示完成了其他规则。

适合：责任上限、付款条件、验收、知识产权、保密或解除的定向复核。

## 5. version_compare

1. 固定 A/B 两个文档版本和比较方向；不能确认先后时仅称 Document A/B。
2. 先匹配条款结构，再做文本差异；区分重编号、格式变化和实质变化。
3. 将变化分类为 `added`、`removed`、`modified_substantive`、`modified_cosmetic`、`unchanged`。
4. 对实质变化分别引用 A、B 的精确证据，并说明对我方权利、义务、金额、时点或风险配置的影响。
5. 特别检查被移除的保护、定义扩张、责任例外变化、付款/验收触发变化、终止权变化和知识产权迁移。
6. 比较结果不自动覆盖任一版本的完整预审结果。

## 6. amendment_trace

1. 按签署日期、修订编号和明确的生效规则排列基础协议及修订。
2. 提取每份修订明确新增、删除、替换的条款。
3. 对目标条款建立“原始语言 → 各次修改 → 候选现行语言”链条。
4. 若修订之间冲突、修订了已删除条款或优先顺序不明，状态为 `conflicted` 或 `human_review`；不得自行选择有效文本。
5. 现行语言必须指向其来源文件和版本。

## 7. redline_draft

只基于已验证发现和已发布企业立场生成修订建议：

1. 确认目标合同版本及待修改条款；
2. 将修改目标、现有文字、建议动作和依赖的商业变量分开；
3. 优先采用删除、替换词语、插入短语或重构子条款；
4. 仅在局部修改会造成歧义时替换整条，并说明原因；
5. 检查修改后定义、编号、交叉引用和相关条款是否仍一致；
6. 输出 `proposal`，不直接修改固定原件，不描述为已接受立场。

如果待确认金额、期限、比例、服务等级或数据处理范围，使用参数和人工任务，不自行填入所谓“市场标准”。

## 8. escalation_draft

仅使用已验证发现和已提供的审批矩阵：

- 定性触发原因：金额阈值、不可接受条款、超出让步、关键缺材料或商业决策；
- 指定审批角色；只有输入明确给出姓名时才使用姓名；
- 附合同原文、企业立场、影响、可选方案、建议和决策期限；
- 输出为草稿，不发送、不审批、不写回外部系统。

若审批矩阵缺失，创建 `approval_matrix_required` 人工任务，不凭经验猜审批人。

## 9. stakeholder_summary

只从已经验证的审查结果生成摘要，并先确定受众：

| 受众 | 优先内容 |
|---|---|
| 采购 | 价格、续约、锁定期、供应商承诺、审批事项 |
| 业务负责人 | 能获得什么、何时交付、失败后怎么办、需要做什么 |
| 财务 | 总成本、付款触发、预付、调价、退款和财务敞口 |
| 安全/IT | 数据流、安全措施、下游处理者、事件、迁移和连续性 |
| 法务/审批人 | 证据、企业立场偏离、法律疑点、选项和剩余风险 |

非法务摘要使用业务语言，保留决定所必需的限制，不加入新的判断。不得因为压缩篇幅而省略关键未决事项或写成“可以签”。

## 10. 修订建议通用要求

- 修改粒度从词、短语、句子到整条依次扩大；能小改则不重写整条。
- 与合同中的定义、编号、主体称谓和语言风格一致。
- 同时说明修改目标、建议文本及仍需业务确认的变量。
- 不把建议文本标成现有合同文字，不承诺其当然有效或必然被对方接受。
- 需要金额、期限、比例等商业选择时使用显式参数和人工任务，不擅自填默认值。

## 11. 质量检查

- 规则范围与请求一致，完整审查覆盖核心包和所有被合同结构触发的专项包；
- 每个确定性发现有有效证据，精确引文可回到固定版本；
- 每个 `not_found` 有充分缺失性证据；
- 解析失败、无权限和材料缺失没有被写成“未发现”；
- 法律依据来源、版本、条款和适用时点可核验；
- 合同事实、专业判断、企业立场和修订建议互相区分；
- 风险严重度说明机制和影响，不由措辞情绪决定；
- 没有单一安全分、自动通过、自动批准或自动外发；
- 人类摘要与结构化结果一致。
