## 1. 文档目的

本稿记录合同审核实现中知识与能力的逻辑分层，以及本轮 MVP 的目标能力。旧版开发文件与本稿不一致时，以本稿确定的业务范围为修订目标；接口、数据、权限、排期和验收仍需在对应开发文档中落地并完成评审。

本稿不裁决 Agent 框架、主开发语言、服务部署形态或知识域之间的调用协议。上述事项留待后续单独讨论。

## 2. 已确认的架构原则

1. 法律知识域与企业知识域是两个独立模块。
2. 法律知识域以权威法律原文及其版本信息为依据；原文查找阶段拟采用 PageIndex 辅助定位。
3. 法律审核 Skill 由律师参与设计和优化，采用严谨、规范、可审查的维护方式，不以自动生成的知识积累替代法律审查。
4. 企业知识域承载公司内部管理规范、审核要求和内部经验；可评估用 LLM-Wiki 与企业 Skill 逐步整理和积累。
5. 企业知识不得改变法律依据的内容或效力，也不得将企业内部要求表述为法律规定。
6. 一项审核可以涉及法律要求和企业要求，但两类结论应能识别其所属知识域及依据来源。

## 3. 逻辑分层建议

```text
合同审核流程
  ├─ 合同类型识别
  ├─ 通用审核能力
  └─ 合同类型专项审核能力
       ├─ 法律审核模块
       │    ├─ 法律审核 Skill（律师参与设计、评审和版本维护）
       │    └─ 法律知识模块（权威原文、版本信息、条款定位）
       └─ 企业审核模块
            ├─ 企业审核 Skill
            └─ 企业知识模块（内部规范、审核要求、审核经验）

审核证据与记录
  └─ 保存每项结论对应的依据、规则/Skill 版本和来源信息
```

此图表达逻辑职责，不表示部署拓扑、服务调用顺序或具体 Agent 编排。后续仍需讨论审核流程何时、如何调用各模块。

## 4. 模块职责边界

| 模块 | 主要职责 | 知识来源与维护方式 | 不承担的职责 |
|---|---|---|---|
| 法律知识模块 | 管理权威法律材料及版本；支持按条款定位原文 | 权威来源；规范采集、版本管理和法律审核 | 不用模型生成摘要替代法律原文或效力判断 |
| 法律审核模块 | 将经确认的法律审查方法组织为可执行审核能力 | 律师参与设计、评审、优化；按规则/Skill 版本管理 | 不从未审阅的自动生成内容中直接形成正式法律结论 |
| 企业知识模块 | 管理企业制度、内部审核标准和可复用经验 | 企业授权材料；可评估 LLM-Wiki 辅助整理，发布前需有企业侧确认 | 不修改或覆盖法律知识，不把企业口径冒充法律要求 |
| 企业审核模块 | 按企业自身管理要求检查合同并给出来源明确的结论 | 企业 Skill 与已确认的企业知识 | 不作超出企业授权范围的规则解释 |
| 审核证据与记录 | 记录结论所依据的来源、版本和审核过程信息 | 审核运行产生的结构化记录 | 不重新解释或改写来源材料 |

## 5. 关于知识积累

法律域与企业域采用不同的知识维护策略：

- **法律域：**原文及版本是依据；法律审核方法由律师参与维护。检索结果应能回到具体来源，模型整理内容不能未经审核就成为正式依据。
- **企业域：**内部规范和审核经验可以逐步积累。LLM-Wiki 可作为候选整理和关联工具；其生成或更新的内容必须经企业审核确认并发布，才能进入正式企业知识，或被企业 Skill 作为正式审核依据。当前由企业指定的知识负责人审核发布；具体审批角色、权限颗粒度和流程后续优化。发布的企业知识应有明确版本；每次审核记录实际使用的已发布知识版本，后续更新不回写或改变历史审核结果。Wiki 知识发布不自动改变 Skill 的审核行为；Skill 需明确引用或纳入已发布知识，并以新 Skill 版本发布后，才影响后续审核。审核记录同时绑定实际使用的 Skill 版本和知识版本。
- **隔离要求：**两个知识域分别管理来源、版本、审核状态和权限。若同一事项同时涉及二者，审核结果分别标注法律依据与企业依据。

`skills/` 中现有 `SKILL.md` 是开发过程中供模型使用的审查方法说明，不代表平台已发布的正式规则。未来平台运行用 Skill 仍采用 MD 文本作为给模型的规范；版本、审批状态、哈希和知识引用可由数据库管理，具体存储方案在实施设计中确定。正式运行时由应用计划限定检查范围和可读取上下文，开发用 MD 不能自行成为发布依据。

## 7. 后续讨论清单

建议继续逐项讨论以下架构主题，本稿不预设其答案：

1. **其他系统数据接入：**合同从哪些内部系统进入，接入何种数据，数据责任和权限如何划分。
2. **关联合同：**如何识别主合同、补充协议、订单、变更单及历史版本之间的关系；如何把关联材料纳入审核上下文。
3. **外部企业信息：**企查查等外部数据源通过何种授权和接口接入，哪些数据可用于审核，如何保存来源、查询时间和结果快照。

5. **知识域调用：**法律模块与企业模块由何种审核阶段触发，结果如何汇总并保持来源区分。

## 8. 内部系统数据接入讨论记录

以下内容记录本轮 MVP 的目标能力和待完善的实施设计。详细接口、数据口径与验收通过相应开发文档分阶段确定。

### 8.1 财务系统

- 当前优先考虑通过 API 接入财务系统，先围绕签约主体的应收、应付状态设计技术接入。
- 财务 API 的主体查询标识使用统一社会信用代码。
- “应收应付”不等于签约方完整的财务状况。更广泛的财务状态及其业务口径需与财务部门进一步确认，不在当前技术讨论中擅自定义。
- 财务数据用于提供审核背景和风险线索；具体状态如何影响审核提示、审批或合同建议，需结合财务和业务规则另行确认。
- MVP 不建设复杂的财务风险评分或综合信用评分；以财务系统提供的应收应付状态和简明背景提示供本次合同审核参考。具体状态口径及提示条件由财务部门确认。
- MVP 财务数据同时包含主体级应收应付汇总和交易明细。交易明细覆盖全部当前未结清和逾期交易，以及最近 12 个月已结清的交易；近期已结清交易可作为双方近期结算合作情况的正向背景。
- 交易明细建议至少提供：应收/应付方向、金额及未结余额、币种、到期日、结清状态、账龄或逾期天数、来源单据标识和数据更新时间。最终字段名和口径以财务 API 实际定义并经财务确认的结果为准；主体/往来口径仍待与财务部门确认。

### 8.2 合同管理系统

合同数据按两个用途维度讨论：

1. **签约方历史合同：**根据签约主体信息查询和选择该主体以往的合同签署情况，作为本次审核的历史背景。MVP 候选列表仅包含曾经签署的合同，可显示合同标题、类型、签署时间、状态和由系统自动生成的合作事项摘要；列表和摘要均不展示合同金额或可反推出金额的信息，避免向无金额权限的工作人员泄露敏感信息。主体相同的历史合同可供工作人员选择；不会仅因同属一个集团就自动扩展到其他子公司。历史合同默认只作背景参考；只有工作人员明确将合同关联到本项目，才作为上下游义务分析的依据。

金额使用与展示分开处理：已选历史合同正文及财务交易明细中的真实金额，在本次任务、数据来源和字段均获授权时，才可进入受控审核上下文。服务端对模型输入、候选摘要、结果、报告、导出和日志统一执行用途与字段级权限；前端只负责在服务端授权结果之上呈现或遮挡。工作人员选择一份合同仅表示希望纳入本次分析，不自动授予系统或模型读取该合同全文、金额的权限。
2. **本次合同的关联合同：**将同一项目中的客户合同与采购合同关联起来，分析客户合同向采购合同传递的交付、验收、期限、质保和责任等义务是否衔接。由于合同对项目的描述可能不同，MVP 中由工作人员手动选择已有合同或上传合同，不依靠项目描述自动配对。工作人员只选择或上传合同，不负责标记合同内容；系统自动识别和标记上游义务，定位相关原文，与采购合同条款进行比对并给出判断。判断需能回溯到上下游合同的具体条款。关联关系用于上下游义务分析，不表示两份合同存在主从法律关系。

**跨主体关联暂不处理：**如果客户合同由我方 A 子公司签署、采购合同由我方 B 子公司签署，判断两者之间的内部义务关系需要建立我方内部法人主体关系本体。该能力超出当前范围，MVP 暂不支持此类跨主体上下游关联分析；后续需单独设计。

#### 上下游义务传递分析：MVP 确认范围

> 本小节状态：讨论已确认，可作为上下游义务传递分析能力的实现依据。本文其他尚未讨论的内容仍为讨论稿。

工作人员负责选择已有上下游合同或上传合同，不负责手工标记条款。系统负责从客户合同中识别上游约定、定位原文，并与采购合同中的相关条款自动比对和判断。每项判断应能回溯到上下游合同的具体条款。

MVP 上下游分析覆盖以下义务类别。系统判断某项要求是否适用于本次交易，不要求把上游约定逐字或机械地复制到采购合同：

| 义务类别 | 识别与比对范围 |
|---|---|
| 工作范围与交付物 | 产品、服务、数量、规格、技术要求、成果形式；检查采购范围是否覆盖客户承诺的内容及规格是否一致 |
| 交付计划 | 日期、里程碑、地点、部署或上线时间；检查供应商交期能否支撑客户期限，并考虑集成和验收时间 |
| 验收与整改 | 验收标准、测试方式、验收期限、拒收和整改流程；检查采购验收条件能否支撑客户验收承诺 |
| 质量、服务与保障 | 质量标准、服务等级、响应时间、可用性、运维支持；检查供应商承诺能否覆盖客户要求 |
| 质保与缺陷处理 | 质保期限、维修、更换、修复和缺陷责任；检查供应商责任能否支撑我方对客户承担的责任 |
| 合规、资质与现场要求 | 许可、行业标准、现场安全、人员资质、客户规则；检查供应商承担的要求及配合义务 |
| 数据、保密与安全 | 保密范围、数据处理、访问控制、安全事件通知、删除和返还；检查供应商义务能否覆盖我方向客户作出的承诺 |
| 知识产权与第三方权利 | 成果归属、许可范围、侵权保证、第三方材料限制；检查采购成果的权利安排能否支持我方向客户交付和授权 |
| 变更与项目配合 | 需求变更、客户审批、接口配合、报告和协作；检查供应商的配合义务，以及费用和工期调整约定 |
| 付款与商业条件 | 客户付款节点、开票、付款前置条件、价格或费用调整；检查上下游安排可能带来的现金流和履约风险，不机械照搬付款条件 |
| 违约责任与风险分配 | 延误责任、违约金、赔偿、责任上限、保险或履约保障；检查供应商责任与我方对客户可能承担的责任之间的缺口 |
| 分包与人员安排 | 分包限制、关键人员、人员替换、供应链要求；检查客户同意要求及供应商的管理责任 |
| 暂停、解除与退出 | 暂停条件、解除权、替代履约、过渡支持、资料返还；检查供应商合同终止时我方能否继续履行客户合同并完成交接 |
| 文件、报告与审计 | 交付文档、进度报告、测试记录、审计配合；检查供应商是否提供验收、汇报或向客户举证所需材料 |

每项比对至少给出上游原文要求、采购合同对应条款、覆盖判断和来源定位。覆盖判断包括：已覆盖、部分覆盖、未覆盖、存在不一致、不适用。付款、违约责任、责任上限等条款应结合交易安排解释差异，不以文本不一致直接推定为缺陷。

> **范围备注：**补充协议作为待审对象的审核逻辑留待后续完成。下方现有补充协议设计内容暂时保留供后续讨论，不作为当前 MVP 的实施要求；后续完成设计时再统一审阅和调整正文。

合同文件本身还需区分主合同、签约时随附的合同附件和后续补充协议。审核补充协议时，先判断当前待审文件的类型；若为补充协议，必须选择其原主合同，主合同是理解补充协议约定的必要上下文。签约时随附的附件作为该合同文件包的一部分提供上下文。

**后续功能的范围设想：**若以后支持补充协议待审，可先考虑直接关联原主合同；多层补充协议链及效力合并须另行设计。这不是当前 MVP 的实施要求。

常规流程审核待签文件。引用已签主合同或附件作为审核依据，不代表重新审核这些文件；签约后的合同风险回顾属于另一个场景，需单独定义。

### 8.3 外部企业信息

- 签约主体身份核验是基础能力，重点用于发现合同签约信息与企业主体信息不一致等情况。
- 经营和信用风险信息可作为本次合同签约审核的重要参考，触发对相关合同条款的重点检查；它属于交易风险提示，不等于合同本身存在缺陷，也不单独形成合同审核问题。
- 外部信息需结合本次合同、交易角色及相关条款解释，并保留来源和查询时间，避免将不相关或过期信号直接当作结论。
- 当前合同审核工具不建设跨合同复用的企业信用档案、综合评分或供应商画像；该类能力属于未来供应商管理平台的范围。
- 该能力有价值，但排在 MVP 实施末段。外部数据服务选择、MCP 或其他接入方式、数据字段和调用权限仍待后续讨论。

### 8.4 审核上下文组装与冻结

**MVP 实现：**不同层次的审核启动前，先为本次审核组装并冻结所采用的信息上下文，使各层审核基于同一组合同材料、关联关系和外部状态。已启用且获授权的财务、合同系统及外部信息在审核启动前查询；审核 Skills 不在审核过程中自行调用这些系统。真实财务与合同系统读取属于 MVP，可安排在实施后半段完成详细接口设计、联调和验收；前半段先固定授权、来源状态、快照及失败语义，并用模拟数据验证流程。模拟数据不能替代最终真实接入验收。

上下文可包含当前待审合同及附件、用户确认的主体信息、选用的历史合同和项目关联合同，以及已启用数据源的查询结果。上下文记录各材料的来源、版本或标识、关联关系和查询时间。合同业务类型在上下文冻结后判断，作为分层审核的第一步。

“冻结”指固定本次审核实际采用的信息及其版本快照，不意味着把所有历史合同或原始数据一次性放入模型输入。各层审核按需读取冻结上下文中的相关材料和条款。审核开始后发现材料或数据需要变更时，应形成新的上下文版本并重新运行相关审核，不能在同一运行中静默替换依据。

**未来实现方向（待后续设计）：**将财务 API、合同管理系统 API、企查查等查询能力登记为平台可用的 Tools。各企业按自身接入情况启用并授权可用工具；审核上下文构建时读取该企业的工具能力声明，只对已启用且获授权的数据源查询。未接入某项可选工具，不构成审核启动的前置条件，也不要求企业提供该来源的数据；审核 Agent 只能调用当前企业已声明可用的 Tools。该机制应支持后续扩充不同系统和外部数据源。

Tool 调用遵循最小必要数据原则：调用参数仅包含完成查询所需的数据。例如外部企业信息查询使用企业名称或统一社会信用代码，财务查询使用必要的主体标识和查询条件，合同系统查询限定于工作人员选择的合同或条款。默认不向外部查询工具发送合同全文。

Agent 在审核过程中发现具体问题所需信息不足时，可针对性调用当前企业可用的 Tool。此类调用及返回结果需纳入本次审核的上下文和审计记录，保留调用来源、查询内容、结果和时间；如何版本化新增信息并更新受影响的审核结论，留待后续设计。运行时应区分工具未接入、查询失败和数据过期等状态，不能将它们混为一类。

### 8.5 上下文缺失与数据不可用

- **后续补充协议待审功能缺少主合同：阻断正式审核。**本规则只在该后续功能启用时适用；当前 MVP 仅审核主合同。
- **企业未启用某项可选 Tool：不阻断审核。**不调用未接入的数据源；仅当本次审核确实涉及该项检查时，提示该项因数据源未启用而未核验，不必在每份报告中罗列所有未接入工具。
- **财务 API 无响应：允许审核继续，但明确提示。**记录数据未取得及其影响范围；依赖该财务信息的检查应标示为未执行或受限，不能将“没有取得数据”解释为“没有风险”。
- **外部企业信息过期：允许审核继续，但明确显示数据时间和过期状态。**相关风险提示应标示为陈旧或不可用；不得把过期数据呈现为当前状态。
- **未关联客户合同：允许采购合同审核正常完成。**项目上下游义务传递分析不是常规审核的前置条件。界面说明本次未执行上下游分析，不单独建设“没有客户合同”与“合同尚未提供”的辨别流程；若文本明确引用客户侧约定，或用户已启动分析却缺少上游材料，可提示相应检查受限。在未取得上游原文时，不得断言上下游条款冲突。
- 对非阻断类数据问题，冻结上下文时应记录数据状态、来源、查询时间和受影响的审核项，使报告能够区分已核实事实、未取得信息和过期信息。

### 8.6 合同类型不确定与专项 Skill 覆盖兜底

以下为当前暂定的 MVP 兜底机制；合同类型分类、混合合同拆分和 Skill 覆盖模型后续仍需深化设计。

- 通用审核在合同类型不确定时仍可继续；不因类型不确定而暂停整个审核。
- 类型不确定时不运行专项 Skill，并在结果中明确说明专项审核未执行及其原因。
- 一份合同包含多类采购内容时，可对已识别且有对应 Skill 覆盖的部分分别运行专项审核。
- 对无专项 Skill 覆盖的混合内容（例如跨软硬件的集成责任），明确提示专项审核未覆盖；不得使报告呈现为该部分已经完成专项审查。
- 上述未覆盖提示用于说明审核范围，不自动构成合同条款缺陷。

### 8.7 审核结果的信息分层

本节为讨论已确认的结果呈现原则。审核结果至少区分以下三类信息：

1. **合同审核发现：**合同条款本身的风险或问题，列明相关合同条款，并给出适用的法律依据、企业要求或规则依据。
2. **签约决策参考：**财务应收应付状态、经营和信用风险信号等背景信息，说明来源、查询时间及与本次交易的关联；这类信息可能影响签约决策，但不自动构成合同条款缺陷。
3. **审核范围与数据提示：**专项 Skill 未覆盖、外部数据不可用或过期、上下游合同未提供等情况，说明本次实际审核范围及信息限制。

上述类别分别呈现，避免将风险背景或数据缺失误表示为合同问题，也避免把未核实信息表示为无风险。

#### 法律要求与企业内部要求冲突

- 同一事项的法律要求与企业内部要求发生冲突时，以适用的法律要求为优先依据。
- 系统应明确提示冲突，并分别列出法律要求及其来源、企业内部要求及其来源；不得将内部要求呈现为高于或替代法律要求。
- 冲突提示应说明可能影响合同效力或履行判断，供审核人员进一步审查；系统不应仅依据内部要求给出与法律要求相反的处理结论。

### 8.8 MVP 审核准备与执行顺序

本节为讨论已确认的 MVP 流程：

1. **上传待审核合同：**MVP 以主合同作为待审对象。工作人员标明待审合同和随附材料；系统不自动判断主合同或补充协议。补充协议作为待审对象的审核流程留待后续。
2. **提取并确认主体信息：**系统提取签约主体等信息，供后续历史合同查找和数据源查询；工作人员可以纠正提取结果。MVP 不推断集团内不同子公司的主体关系。
3. **选择签约方历史合同：**按已确认的签约主体查找历史合同，由工作人员选择作为背景参考的记录；不自动将该主体的全部历史合同作为本次审核依据。
4. **选择项目上下游合同：**工作人员手动选择已有客户合同或上传客户合同。系统不根据项目描述自动配对；未关联客户合同不阻断采购合同的常规审核。
5. **查询已启用的数据源：**对本企业已启用且获授权的 API/Tool 查询财务应收应付、外部企业信息等。按最小必要数据原则提供查询参数；未接入数据源不作为前置条件。
6. **预览并冻结上下文：**工作人员核对本次审核的待审合同、附件、选中的历史合同和上下游合同，以及已取得的数据及其来源、时间和状态；确认后冻结本次审核上下文。
7. **启动分层审核：**上下文冻结后，先判断合同业务类型，再运行通用审核，最后运行类型明确且有 Skill 覆盖的专项审核。类型不确定时不暂停，继续通用审核但不运行专项 Skill；混合类型按已有 Skill 覆盖范围分别审核，并披露未覆盖部分。
8. **呈现审核结果：**按“合同审核发现”“签约决策参考”“审核范围与数据提示”三类信息分别呈现。

冻结后，各审核层读取同一份上下文。需要替换材料或更新查询结果时，形成新的上下文版本并重新运行受影响的审核。

## 9. 待确认事项

- 法律知识和企业知识分别由谁负责维护、审核和发布；
- 法律原文的权威来源、修订跟踪和版本生效模型；
- 企业 Wiki 内容从草稿到正式发布的审核门槛；
- 外部数据和 MCP 工具的准入、权限与审计要求；
- 逻辑模块落实到进程、服务或部署单元的具体方案。
