## 1. 产品定位

从零建设一个以审计案件为中心的合同审计平台。平台综合合同原文、企业制度、法律规范、财务往来、历史及关联合同、外部数据和人工意见，对合同签署、变更、续签及事后复核提供可追溯的审核建议。

平台可以独立接受用户上传，也可以作为传统合同管理系统中的审核节点。它提供事实、风险、证据、修改建议和结构化结论；原合同管理系统或有权限的人员负责正式流程决定。

当前仓库只提供设计和测试经验，不产生旧系统兼容、迁移、双跑或退役义务。

## 2. 已确定的架构原则

1. AuditCase 是业务中心，AuditRun 是一次固定输入、规则和版本下的执行。
2. Go 模块化单体作为首期形态，API 与 Worker 可分进程；先不拆六个微服务。
3. 六个领域是产品能力边界，不强制对应六个自主 Agent。
4. 正式审核由固定 AuditPlanSnapshot 和持久工作流驱动，Agent 不能跳过必审项或决定最终阻断。
5. Eino 用于结构化模型调用、受控工具循环和适合 Agent 的任务；案件状态、重试、权限、快照和结果由应用控制。
6. 共享事实层为本次案件提供唯一、固定、可追溯的事实视图；不同来源冲突被保留和处置，不由模型自行选值。
7. 法律、企业制度和外部数据都是有来源与版本的输入；模型推理不是证据。
8. 确定性计算负责金额、期限、阈值、权限和聚合约束；模型负责语义判断、解释、材料缺口与文字表达。
9. 所有外部 JSON 先由 Adapter 确定性解析、映射、校验为标准化信息，再交给模型；模型不猜字段。
10. PostgreSQL、对象存储和持久任务表是首期基础设施方向；图数据库、通用 ETL 和独立工作流引擎按实际需要再引入。

## 3. 端到端业务流程

```text
用户上传 / 合同系统事件
        ↓
创建或绑定 AuditCase，固定合同版本、审批轮次和用途
        ↓
读取合同、上游意见及授权外部数据
        ↓
Adapter 解析校验 → 主体归一 → 事实候选 → 冲突/人工确认
        ↓
形成不可变 InputSnapshot + FactSetSnapshot
        ↓
根据合同类型、角色、组织、金额等生成 AuditPlanSnapshot
        ↓
持久工作流执行单域检查和跨域检查
        ↓
候选结果经过 Schema、证据、引用、口径及权限校验
        ↓
固定策略生成最低结论约束，模型组织解释和报告
        ↓
人工复核 / 补材料 / 修改方案 / 局部或全量重审
        ↓
平台形成决定记录，或向合同管理系统回写结构化结果
```

执行失败、数据不足与专业不通过是不同状态。未获得数据或接口超时不能解释成“未发现风险”。

## 4. 六领域能力

| 领域 | 主要输入 | 核心能力 | 主要边界 |
|---|---|---|---|
| 法律审核 | 合同、事实、规则包、法律知识 | 条款完整性、合法性与交易风险；修订建议 | 不凭模型记忆编法条，不把检索未命中直接当缺失 |
| 企业内部审核 | 制度、授权矩阵、流程材料、企业规则包 | 制度、权限、审批和材料符合性 | 租户不能覆盖平台法律规则；未授权意见不构成豁免 |
| 财务审核 | 主体映射、往来余额、账龄、预付、核销等 | 判断存量财务事实与新交易条件是否相容 | 不要求开放全库，不把我方应付问题说成对方信用问题 |
| 合同关联 | 当前、历史、上下游及主补合同关系 | 变更、重复承诺、上下游条件和历史问题 | 同一供应商不自动等于上下游，低置信关系不作阻断 |
| 外部核查 | 标准化外部记录与主体匹配 | 工商、司法、处罚等事实与交易相关性 | 查询失败不等于无风险，单条记录不自动禁入 |
| 综合审计 | 前五域结构化结果、共享事实、跨域规则 | 冲突、组合风险、材料覆盖和行动建议 | 不覆盖单域结果，不用自由总结替代固定策略 |

综合审计由“显式跨域检查 + 固定聚合策略 + 可读报告”组成。它不是第六个自由判断所有问题的超级 Agent。

## 5. 案件入口与合同管理系统关系

系统同时支持：

- 用户直接上传进行预审；
- 用户将已进入流程的合同手工发起辅助审查；
- 合同管理系统在指定审批节点调用；
- 先预审，后绑定合同流程；
- 对已审批或签约版本进行事后复核。

每个案件必须明确流程主系统、合同版本、审批轮次、审查目的和报告用途。预审结果只有在材料、规则、权限、数据时效和检查范围仍一致时才可复用，否则创建新运行。

合同节点调用采用异步任务。源系统撤回、换版本或重提时，旧结果不再适用于当前节点。首版读取和写回权限分离，默认只读；审核完成不自动等于节点批准。

上游意见保留作者、节点、时间、目标版本、条件和解决状态。它是待验证的意见记录，不自动成为事实或豁免。

## 6. 数据体系

### 6.1 五类数据必须分开

| 类型 | 作用 |
|---|---|
| 语义模型/本体 | 定义法人、合同、付款义务、往来、控制关系等对象和关系 |
| 规范知识 | 保存法律法规和企业制度的版本化原文 |
| 可执行规则 | 描述适用范围、检查方法、证据、例外和风险策略 |
| 案件事实 | 描述本次交易实际约定、系统记录或人工确认的事项 |
| 审计判断 | 说明事实与规范之间是否存在问题以及下一步动作 |

### 6.2 事实与证据

事实包括类型化值、单位/币种/税口径、主体、业务与观察时间、来源、映射版本、确认状态和版本。合同约定金额、流程表单金额、财务余额和实收实付是不同事实，不能互相覆盖。

来源权威按字段和用途定义：合同原文证明约定，财务快照证明账内记录，流程实例证明审批状态。冲突生成 FactConflict；未解决且影响判断时转人工或不确定。

证据至少覆盖原文、表格、外部记录、计算证明、人工确认、规范引用和缺失性证据。证据真实存在与证据足够支持结论分别验证。

## 7. 财务系统接入摘要

首版不追求全量总账，优先获得五类只读能力：

1. 本方签约法人、账套和对方客户/供应商编码的主体映射；
2. 指定双方、币种及截止日的应收、应付、预付和预收分项；
3. 同口径的账龄、到期或逾期摘要，并说明日期基准；
4. 当前合同、项目或订单与往来记录的可靠关联；
5. 快照时间、覆盖范围、单据过滤、核销和完整性说明。

第二批按场景接入收付款与核销、争议款、信用额度、集团分法人视图、票据、账户核验和发票等数据。

权限有限时可以只提供汇总或源端核验结果。结论强度随数据能力降低：没有合同关联只能做主体级分析，没有到期日只能报告账龄，缺少支付与核销明细不能判断逐笔重复支付。

第一批候选检查：

- 对方已有逾期应收，新销售合同继续给予宽松账期；
- 存量预付仍未结，新采购合同又要求高比例预付；
- 本方已有到期应付，续签仍依赖对方持续供货；
- 收款方或账户变更与财务主数据不一致；
- 结算金额与合同付款期次不一致。

## 8. 合同数据与关系

从合同管理系统读取当前版本、附件、主体、项目、金额、状态、上游意见、历史合同和显式关系。搜索“全部历史合同”必须说明授权范围、分页完成情况和截断状态。

关系可信度顺序为：源系统明确关系、授权人员确认、稳定业务标识匹配、内容检索或模型推断。每条关系记录类型、两个合同版本、来源、方法、置信度、状态和有效期。

首批检查关注主合同与补充协议、框架与订单、续签与历史未完义务、重复承诺，以及明确上下游合同之间的交付、付款、责任和保障错配。

## 9. 法律知识、企业制度与 Skills

需要建设版本化法律知识库，但不默认把民法典、公司法等全部全文放入每次上下文。

- 规则固定绑定必要法律依据及版本；
- 按合同类型、角色、地域和相关时间检索补充依据；
- 条文保留章节、定义、例外、引用关系和相邻上下文；
- 必要时允许读取某部法律全文；
- 报告引用必须能回到登记的规范原文核验。

企业制度保存适用组织、业务、金额范围、生效区间、发布主体和例外。法律与制度共用规则包、审批、版本、评测和快照底座，但维护权限隔离。

结构化规则包是执行定义的唯一作者源。Skill/Prompt 是由规则和执行配置生成或绑定的受控产物，不能形成平行真相源。租户首版不执行任意脚本。

## 10. 跨域检查

成熟组合场景定义为 CrossDomainCheck，明确：

- 适用交易场景；
- 所需事实、单域结果和关系；
- 时间容差与数据覆盖要求；
- 确定性计算、语义判断点、反例和例外；
- 证据及人工复核策略。

执行层编译依赖图。事实变化、合同版本变化或人工纠正后，相关结果失效并重算。多个领域引用同一基础风险时用 risk_instance_id 归并，不重复计分。

模型可做受控探索，发现固定规则外的组合问题；探索结果作为候选，经证据和人工确认后，才可能沉淀成正式跨域规则。

## 11. 人工闭环与结果责任

完整闭环包括查看证据、补材料、纠正事实、局部/全量重审、修改方案、候选文档、人工决定和外部流程回写。

模型只生成修改草稿；确定性修改器基于固定文档版本产生新版本，原件和旧结果保留。外部节点案件由合同管理系统掌握正式文件和审批流转。

报告必须同时呈现：

- 审查对象及版本；
- 事实及来源；
- 发现、证据和适用依据；
- 数据覆盖与限制；
- 建议动作及需人工决定的问题；
- 使用的计划、规则、知识、连接器、模型和执行器版本。

## 12. 工程与运行要求

核心对象包括 AuditCase、ExternalBinding、DocumentVersion、AuditPlanSnapshot、InputSnapshot、FactSetSnapshot、AuditRun、CheckExecution、CheckResult、Evidence、ResultDependency、DecisionSnapshot 和 HumanTask。

任务采用至少一次执行，使用幂等提交、租约 fencing 和事务性事件/outbox。模型和网络调用不持有数据库事务。业务事件支持续传；事件序号原子分配。

模型只获得任务所需数据；租户、法人/账套、案件、字段和用途权限由应用校验。敏感字段可在确定性工具中比较，只向模型提供结果和受控引用。

观测记录业务事件、模型与工具版本、成本、延迟、错误和数据覆盖，不保存模型隐藏思维链。

## 13. 分阶段建设

| 阶段 | 交付 |
|---|---|
| Phase 0 定界与样本 | 选定首个合同类型、角色、客户和场景；拿到接口样本；形成初始事实、规范和金标 |
| Phase 1 首个案件闭环 | 直接上传或只读导入；法律及少量企业检查；证据、人工复核和报告 |
| Phase 2 真实数据价值 | 一个财务往来接口、合同历史/关系读取、首批跨域检查 |
| Phase 3 流程接入与重审 | 合同节点调用、上游意见、异步回写、补材料、版本变化和依赖重审 |
| Phase 4 治理与扩域 | 制度作者、审批评测、外部核查、更多规则和数据源 |
| Phase 5 试点上线 | 完整操作链、容量成本、恢复告警、运维与业务签署 |

具体工期要在首个试点范围、接口权限、材料格式和验收标准确定后估算。

## 14. 当前仍需补充或决策的事项

### A. 首期产品边界（最高优先级）

1. 首个合同类型和交易方向：采购、销售、服务、租赁或其他。
2. 首个使用者与责任人：业务、法务、财务、审计还是合同管理员。
3. 首期是预审工具、正式审批节点，还是两者都做但分阶段开放。
4. 首批必须交付的法律、企业、财务和跨域检查清单。
5. 哪些结论仅提示，哪些必须人工复核，哪些可以阻断流程。

这些决定会直接收敛事实 Schema、接口字段、规则、页面和金标。

### B. 数据与连接器契约

1. 财务、合同系统各一份成功、空结果、部分结果和错误的脱敏响应样本。
2. 主体统一标识和人工确认机制。
3. 外部数据的存储、保留、刷新、历史回放和删除要求。
4. 接口版本变更通知、Schema 漂移检测及能力降级策略。
5. 合同管理系统节点的认证、幂等、撤回、换版、超时和回写状态。

### C. 事实冲突与人工权限

需定义谁可以确认主体映射、金额口径、合同关系和事实冲突；确认是否只对本案件有效，是否能沉淀为租户级映射；多人意见冲突如何升级；确认后哪些结果必须失效重审。

### D. 规则与知识运营

需明确平台法务、客户制度管理员、财务负责人和产品团队的 DRI；法律更新监测频率；规则变更审批和紧急停用；制度冲突优先级；评测集维护和历史结果复核策略。

### E. 评价指标和金标

除准确率外，需签署：

- 高风险漏报、误报；
- 必审项覆盖率；
- 证据定位与支持程度；
- 主体/合同关系误匹配；
- “无法判断”使用质量；
- 跨域检查的新增有效发现；
- 重复执行稳定性、成本和延迟。

金标按合同类型、角色、规则、缺材料、边界和组合反例覆盖；20 份只作为种子。

### F. 安全、合规和部署

需确认私有化/专有云/公有云形态、模型出网、数据驻留、敏感字段策略、密钥托管、日志脱敏、审计留存、灾备目标、连接器网络边界及第三方数据许可。

### G. 非功能目标

需在试点前给出预计并发、合同大小/页数、单案领域数、最长人工等待、节点 SLA、单案成本上限、恢复时间目标和数据保留年限。这些指标决定任务表是否足够、模型策略和部署规模。

### H. 产品交互与责任表达

需设计事实冲突确认、数据覆盖说明、跨域风险归并、上游意见对比、修改建议确认和人工最终决定的页面。报告与界面都要清楚区分事实、规则判断、模型建议和人工决定。

## 15. 下一步建议

下一步不继续扩写抽象架构，直接制作“首个试点定义包”：

1. 选定一个合同类型、交易方向和典型审查角色；
2. 选定直接上传或只读导入作为首个入口；
3. 提供合同、上游意见、财务往来和历史合同的脱敏样本；
4. 选出 10～20 个单域检查和 2～3 个跨域检查；
5. 为每项检查写清事实依赖、依据、证据、反例和数据不足结果；
6. 定义报告样式、人工复核点和试点验收指标；
7. 据此冻结 v1 领域模型、接口和可执行 backlog。

完成这个定义包后，技术 Spike 和首个纵向切片会有真实验收目标，工期估算也会更可信。
