## 1. 建设结论

建议将本项目建设为“可审计的合同决策支持平台”，而不是“能聊天的合同机器人”或“六个 Agent 的集合”。

正式产品应形成以下闭环：

```text
固定审查对象和用途
    → 固定材料、事实、规范、规则和权限快照
    → 按计划执行必审检查
    → 对每项结论校验证据与适用依据
    → 对缺材料、冲突和越权事项转人工
    → 形成结构化结果、报告与决定记录
    → 材料或规则变化后定向重审
```

建设上坚持四条主线：

1. **业务真相由平台掌握。** 案件、版本、规则、事实、证据、任务和决定均由应用数据库持久化；模型或 Eino checkpoint 不是业务真源。
2. **规则决定“审什么”，模型协助“怎么看”。** AuditPlanSnapshot 固定必审项；模型只能提交候选事实、槽位和说明，不能删减检查或批准案件。
3. **证据强度决定结论强度。** 未查到、无权限、接口失败、事实冲突和确有风险分别表达，禁止统一为“未发现风险”。
4. **先做一个可上线纵向切片。** 首期只做一个合同类型、一个交易方向、一个使用角色和少量高价值跨域场景，验证完整闭环后再扩域。

## 2. 首期产品边界

### 2.1 推荐试点

若当前尚无客户指定，建议以“**采购方视角的服务/软件采购协议预审**”为首个试点，入口采用“**用户直接上传 + 合同系统只读导入**”。理由是：

- 法律、企业制度、付款条件、历史合同和财务往来均有明确价值；
- 合同数量通常足够形成金标，条款结构比综合工程类合同更稳定；
- 可先提供决策支持，不必一开始承担原合同系统节点推进风险；
- 后续容易叠加 SaaS、数据处理协议、订单和补充协议规则包。

这是排期基线，不代替 Phase 0 的业务签署。若客户已有明确场景，以客户选定场景替换，但仍保持“一类合同、一个方向、一个主要角色”。

### 2.2 首期做什么

- PDF/DOCX/扫描件上传、解析、页码及条款定位；
- 案件、材料版本、输入快照、审计运行和历史结果；
- 10～20 个法律原子检查、3～5 个企业制度/授权检查；
- 一个真实财务往来只读接口或可替代的稳定模拟接口；
- 当前合同及历史/关联合同只读查询；
- 2～3 个跨域检查；
- 事实冲突、补材料、人工复核、审批上报和定向重审；
- 结构化报告、证据回看、数据覆盖与限制说明；
- 租户/案件权限、审计日志、模型与规则版本追踪。

### 2.3 首期不做什么

- 不同时覆盖采购、销售、租赁、劳动、工程、投融资等全部合同；
- 不建设六个可自由协商或投票的 Agent；
- 不以单一“合同安全分”决定通过或阻断；
- 不让租户上传任意脚本或直接编辑生产 Prompt；
- 不预建通用低代码 ETL、图数据库或独立工作流平台；
- 不自动签署、自动批准或在无人工授权时推进原合同流程；
- 不承诺模型生成文字逐字可重放，只重放固定输入、确定性计算和业务状态。

## 3. 产品责任边界

平台输出分为四层：

| 层级 | 输出 | 责任边界 |
|---|---|---|
| 事实层 | 合同约定、流程状态、财务记录、外部记录 | 必须有来源、版本、时点和覆盖范围 |
| 检查层 | 规则是否适用、是否偏离、材料是否充分 | 由已发布规则与验证器约束 |
| 建议层 | 修改建议、谈判优先级、补材料和上报建议 | 明确标为模型或规则建议，不冒充原文或正式法律意见 |
| 决定层 | 接受、整改、例外、阻断、回写 | 仅由具备权限的人或固定企业政策作出并留痕 |

对外文案建议使用“审查建议”“辅助审核”“需人工复核”，避免把系统描述成能够替代执业律师或企业有权审批人的主体。

## 4. 总体技术架构

```text
Web / 合同系统 / OpenAPI
            │
      API Gateway + IAM
            │
  ┌─────────┴──────────────────────────────┐
  │ Go 模块化单体                         │
  │                                       │
  │ cases / documents / facts / plans     │
  │ execution / checks / decisions        │
  │ knowledge / policies / integrations   │
  │ collaboration / reports / auditlog    │
  └─────────┬──────────────────────────────┘
            │
  ┌─────────┼──────────────┬───────────────┐
  │         │              │               │
PostgreSQL 对象存储   检索索引/向量   Model Gateway
  │                         │               │
持久任务表/Outbox      法规/制度/合同       Eino
                                            │
                                    受控模型与工具调用
```

### 4.1 Go 应用负责

- 身份、租户、权限和用途控制；
- AuditCase、AuditRun、快照、状态机和幂等；
- 计划编译、依赖 DAG、任务领取、租约和重试；
- 规则适用性、确定性计算、证据校验和最低结论；
- 外部连接器、事务 outbox、回调与审计日志；
- 对模型输入做最小化裁剪，对模型输出做 Schema 和业务验证。

### 4.2 Eino 只负责

- 结构化模型调用；
- 条款语义抽取、分类和建议草稿；
- 有明确工具白名单、轮次与预算的局部 ReAct；
- 适合图编排的单次检查内部步骤；
- 必要的 interrupt/resume 技术能力验证。

即使 Eino 提供 checkpoint，外层案件任务、人工等待和业务恢复仍由平台持久工作流拥有。必须调用的工具由应用直接调用，不依赖模型“自觉选择”。

### 4.3 首期基础设施

- PostgreSQL：业务对象、任务、规则元数据、事件和审计日志；
- S3 兼容对象存储：原件、解析产物、快照、报告；
- PostgreSQL 全文或独立检索服务：按首期规模选择；
- Redis：只用于缓存、短租约或限流，不保存业务真相；
- OpenTelemetry：请求、任务、模型、工具、成本和错误链路；
- Secret/KMS：连接器密钥、模型凭证和加密材料；
- 部署形态优先容器化单体，API 与 Worker 可独立扩容。

## 5. 核心业务模型

首版必须稳定以下对象，不要从页面表单反推数据库：

| 对象 | 关键含义 |
|---|---|
| AuditCase | 一次业务审查事项；绑定租户、用途、流程主系统和责任人 |
| DocumentVersion | 不可变材料版本；保存内容哈希、解析器版本和定位坐标体系 |
| ExternalBinding | 外部合同、流程、节点、轮次及请求幂等身份 |
| InputSnapshot | 本次运行使用的全部材料、意见和外部数据快照 |
| FactSetSnapshot | 通过验证的类型化事实集合及未决冲突 |
| RulePackage / RuleDefinition | 唯一结构化执行定义及版本 |
| AuditPlanSnapshot | 本次适用检查、槽位、依赖、权限、依据和预算 |
| CheckExecution / SlotState | 一项检查的持久执行及槽位收敛状态 |
| Evidence | 原文、表格、记录、计算、规范、人工确认或缺失性证据 |
| CheckResult | 不可变的结构化检查结果及不确定性 |
| HumanTask | 补材料、事实确认、专业复核、例外审批或发布审批 |
| DecisionSnapshot | 有权人员在固定结果版本上的决定 |
| ResultDependency | 事实或规则变化后的失效和重审依据 |

任务状态与专业判断状态必须分列。`failed` 是执行失败，`issue_found` 是成功执行后发现问题，两者不可混用。

## 6. 规则、知识与 Skill 工程

### 6.1 三个真源

- **规范原文真源**：法律法规、司法解释、企业制度的版本化原文；
- **规则真源**：机器可执行的 RuleDefinition；
- **案件真源**：固定输入下的事实、证据、检查和人工决定。

Skill/Prompt 是由规则、执行配置和模板编译出的带哈希产物，不成为第四个独立真源。

### 6.2 推荐目录与发布单元

```text
rule-packs/
  legal-core/
    package.yaml
    rules/
      liability-cap.yaml
      payment-conditions.yaml
    skills/
      liability-cap.md
    evals/
      positive/
      negative/
      missing-material/
      boundary/
  tenant-positions/<tenant>/
  finance-counterparty/
  cross-domain/
```

每条规则至少包含：适用条件、前置事实、必填槽位、证据政策、确定性执行器、语义任务、例外、最低风险、人工路由、工具白名单、预算及评测样例。

### 6.3 从现有 skills 吸收什么

| 现有实践 | 产品化方式 |
|---|---|
| commercial-legal 的审查指引与交易角色 | 建成 LegalPosition、让步范围和适用性策略 |
| vendor-agreement-review 的精确引文、最小修订、上报 | 建成偏离检查槽位、ModificationProposal、ApprovalRoute |
| tabular-review 的类型化字段与状态 | 建成强类型 SlotDefinition，并保留 `not_present / unclear / needs_review` |
| amendment-history / compare | 建成版本链、条款级差异和当前有效文本候选 |
| escalation-flagger | 建成可执行审批矩阵，不由模型自由决定审批人 |
| supervisor-review-queue | 建成 HumanTask 队列和批准/退回/编辑后批准日志 |
| matter-workspace | 建成租户、案件和用途隔离，禁止跨案件隐式读取 |
| policy-diff / gap tracker | 建成规范变更影响分析、规则失效与整改闭环 |
| 本地 risk_engine 的关键词/正则 | 仅作候选召回和回归样例，不作最终法律结论 |

### 6.4 明确淘汰什么

- 固定权重的模型安全分；
- 多 Agent 投票形成法律真值；
- 关键词命中直接定高风险；
- “违约金超过合同额某固定比例即违法”等脱离案情的硬编码；
- 未经版本核验的法条说明和通用修订模板；
- 只有 Markdown、没有结构化结果与证据关系的输出。

## 7. 首批检查建议

### 7.1 法律与企业检查

优先选择 12～15 项：主体一致性、授权材料、标的范围、附件完整性、价税口径、付款触发、交付验收、责任上限、免责例外、违约补救、期限续约、解除及后果、保密、知识产权、争议解决。

企业检查优先选择 3～5 项：合同模板偏离、签署权限、金额审批层级、高比例预付审批、数据/系统采购专项审批。

### 7.2 首批跨域检查

1. **存量预付未结 + 新合同高比例预付 + 保障不足**；
2. **历史逾期应收 + 新销售账期宽松 + 信用政策不匹配**（若试点为采购场景，可后置）；
3. **补充协议改变付款或保障 + 存量义务未处置**；
4. **上游附条件意见 + 新版本未落实**。

首期只承诺其中 2～3 个与真实数据条件相符的场景。

## 8. 关键产品页面

首期页面按任务闭环设计：

1. **案件工作台**：审查对象、版本、用途、运行状态和责任人；
2. **材料与解析页**：文件清单、解析覆盖、页码/条款结构和异常页；
3. **事实与冲突页**：候选事实、来源对照、确认和适用范围；
4. **审查结果页**：按风险/领域/行动分组，原文与依据并列展示；
5. **人工任务队列**：补材料、复核、审批、退回和截止时间；
6. **版本与重审页**：材料差异、失效结果和重算范围；
7. **报告页**：结论、覆盖、限制、建议和决定记录；
8. **规则治理页（后期）**：规则草稿、评测、审批、发布和紧急停用。

界面不得只展示“红黄绿”。每个问题至少可展开看到：审查对象、事实、原文、规范、判断、限制、建议和负责人。

## 10. 建议阶段与阶段门

以下为 8～10 人核心团队的规划基线，不是未经 Phase 0 确认的交付承诺。

| 阶段 | 建议周期 | 退出门 |
|---|---:|---|
| Phase 0 定界与技术 Spike | 3～4 周 | 试点定义包获签；样本、接口和金标可用；文档解析与模型结构化输出 Spike 通过 |
| Phase 1 案件闭环 Alpha | 5～6 周 | 上传至报告全链路；10～20 个检查；证据门禁、人工任务、重启恢复通过 |
| Phase 2 数据与跨域 Beta | 4～5 周 | 至少一个真实财务接口、一个合同关系接口、2～3 个跨域检查通过真实样本验收 |
| Phase 3 流程与重审 Pilot | 4～5 周 | 节点调用/只读导入、换版、撤回、补材料、定向重审、回调异常验证通过 |
| Phase 4 治理与上线 | 3～4 周 | 安全、容量、成本、备份恢复、规则发布、运维手册和业务签署完成 |

建议总基线为 **19～24 周**。若首期必须直接进入合同系统正式审批节点，应把最小节点接入提前，但不能跳过只读演练和失败场景验证。

## 11. 团队配置

建议核心团队：

- 1 名产品负责人/业务分析；
- 1 名平台/领域架构师；
- 3 名 Go 后端工程师；
- 1～2 名 AI/知识工程师；
- 1 名文档/OCR 或数据工程师；
- 1～2 名前端工程师；
- 1 名 QA/自动化工程师；
- 法务、财务、信息安全和合同系统负责人作为兼职 DRI。

法务 DRI 不是“需求顾问”，而是规则、法律依据、金标和发布门禁的签署人。财务 DRI 对余额、账龄、到期和集团口径负责。

## 12. 验收指标建议

指标需在 Phase 0 用真实样本校准并签署。建议初始门槛：

| 类别 | 建议门槛 |
|---|---|
| 计划覆盖 | 适用关键检查执行覆盖率 100% |
| 高风险召回 | 独立验收集关键高风险召回率 ≥95% |
| 证据定位 | 引文可定位且逐字匹配率 ≥98% |
| 证据支持 | 高风险结论具备充分支持证据率 100% |
| 误通过 | 应为缺材料/冲突/无法判断却自动通过的比例 ≤1% |
| 主体映射 | 错误自动合并率 0；不确定映射必须转人工 |
| 稳定性 | 同模型与同快照结构化关键字段一致率 ≥98% |
| 恢复 | Worker 中断、重复投递、回调重试不产生重复业务结果 |
| 隔离 | 跨租户、跨案件未授权读取事件 0 |
| 性能 | 常规 100 页以内合同 P95 在试点签署 SLA 内完成 |
| 成本 | 单案模型、OCR、检索成本可观测且不超过签署预算 |

不要把“总体准确率”作为唯一指标。应按规则、槽位、证据、状态和风险级别分别统计，并保留失败样本。

## 13. 安全与合规基线

- 数据分类分级，合同正文、个人信息、财务信息、商业秘密分别设策略；
- 所有模型调用经过 Model Gateway，执行租户/字段/用途过滤与脱敏；
- 明确模型供应商是否留存、训练、跨境处理输入，合同上形成书面约束；
- 个人信息遵循目的明确、最小必要、保存期限、访问/删除和委托处理管理；
- 原件、快照、证据、报告、日志分别定义留存与删除规则；
- PostgreSQL 应用租户过滤与 Row-Level Security 双层防护，并对表所有者绕过风险做专门测试；
- 外部 JSON、网页和文档内容均视为不可信数据，防范提示注入、恶意链接和超大响应；
- 高权限工具、回写、导出和规则发布采用双人或分权控制；
- 生成内容是否适用显式/隐式标识、算法备案或安全评估，应按部署对象和是否向公众提供服务做专项法律评估，不能仅凭“企业内部系统”或“使用大模型”一概判断。

当前建设至少应对照《个人信息保护法》《网络数据安全管理条例》及适用的生成式人工智能治理要求。面向公众提供生成式人工智能服务与企业内部应用的适用范围并不相同；若提供导出、发布或公众服务能力，应重新核验标识等义务。

## 14. 前 30 天行动清单

### 第 1 周：冻结试点问题

- 召开产品、法务、财务、合同系统、安全五方工作坊；
- 签署合同类型、交易方向、入口、使用者、责任人和报告用途；
- 选定 10～20 个单域检查和 2～3 个跨域检查；
- 明确提示、人工复核、整改和阻断的责任边界。

### 第 2 周：拿到可验证输入

- 收集 30～50 份开发样本及独立验收样本框架；
- 获取合同、历史合同、上游意见和财务接口的成功/空/部分/失败脱敏样本；
- 固定文档定位坐标、主体标识、金额和时间口径；
- 输出能力—字段—语义—权限—检查矩阵。

### 第 3 周：冻结契约

- 评审核心对象和状态机；
- 定义 RuleDefinition、SlotDefinition、Evidence 和模型结构化输出 Schema；
- 建立首批规范依据目录与 LegalPosition；
- 完成金标指南、争议裁决流程和评测脚手架。

### 第 4 周：完成纵向 Spike

- 跑通一份真实结构合同：上传、解析、定位、计划、检查、证据、人工暂停、恢复和报告；
- 验证 Worker 重启、重复投递、模型超时、解析缺页和接口部分返回；
- 给出真实延迟、成本、正确性和未决风险报告；
- 只有通过阶段门，才冻结 Phase 1 backlog 与承诺工期。

## 15. 立项时必须签署的决策

在进入正式开发前，以下问题不能继续悬空：

1. 首个合同类型、交易方向、使用者和流程主系统；
2. 首批检查及每项关键槽位；
3. 谁能确认主体、事实、关系、例外和最终决定；
4. 财务及合同接口的真实能力、口径、权限和负责人；
5. 模型部署、数据出境/驻留、日志和留存策略；
6. 金标来源、领域仲裁人和验收阈值；
7. 生产规则的发布、回滚、紧急停用和法规更新 DRI；
8. 节点超时、系统故障或数据不足时，原合同流程如何处置。

## 16. 最终建议

现有方案可以作为正确的架构底稿，但要进入建设，关键不是继续扩写“六领域”概念，而是把首个场景压缩成可验证的工程契约。

建议立即启动“Phase 0 试点定义包”，并以一个真实合同样本贯穿材料、事实、规则、槽位、证据、人工和报告。只要这个纵向切片能够证明：**必审项不会漏、证据不能伪造、缺数据不会误通过、人工决定可追溯、变化后能够正确重审**，平台就具备扩展到六领域的可靠底座。
