## 1. 核心决策与范围

1. 以审计案件 AuditCase 为中心，采用 Go 模块化单体，API 与 Worker 可分进程部署。
2. 保留法律、企业内部、财务、合同关联、外部核查、综合审计六个产品视角；领域模块数量不决定 Agent 数量。
3. 正式审计由应用固定计划、持久化工作流执行；对话 Agent 负责意图理解、解释和提出业务命令，不拥有强制项调度和最终阻断权。
4. 所有检查基于固定的共享事实版本、证据及规范版本。来源冲突显式保留，不能通过摘要或模型选择隐藏。
5. 财务接入以本方公司/授权集团范围与合同对方的应收应付及往来风险为核心；不假定开放全库、全部账套或任意查询。
6. 合同管理系统是传统合同流程审批工具：提供当前合同、上游意见、历史及上下游合同，未来可在流程中调用本平台作为一个节点。
7. 同时支持用户直接上传、合同系统发起、先预审后绑定、事后复核；每个案件明确流程主系统、材料版本与报告用途。
8. 未来结构尚未确定的外部接口通过参考数据源接入；接入时确定字段语义，由适配器完成确定性解析、映射和校验，再将标准化信息提供给审核模型。模型不猜测字段含义或生成映射。
9. 法律与企业制度共用知识、规则包和发布基础设施，区分维护权限。法律全文是规范来源，规则包是可执行检查定义，Skill 是受控执行说明。
10. 综合审计包含显式跨域检查、固定决策策略和报告生成，不只是让模型总结五域摘要。
11. PostgreSQL、对象存储和持久任务表作为初始基础设施方向；独立工作流引擎、图数据库、通用集成平台不预先引入。
12. 先完成有真实业务价值的案件闭环，再扩展连接器、合同类型和制度作者功能；上线依据新产品金标、试点和运行验证。

## 2. 已确定事项与待验证边界

| 项目 | 已确定 | 尚需确认 |
|---|---|---|
| 财务系统 | 用友、金蝶等企业内部系统；权限有限；应收应付关系最优先 | 产品/版本、账套及组织范围、具体读接口、金额口径、数据时效和明细可见性 |
| 合同管理系统 | 合同基础数据、上游意见、历史及关联合同；未来流程节点 | 是否能下载版本化附件、关系是否显式存在、事件/回调能力、节点超时与回写契约 |
| 其他数据源 | 可能仅有 JSON 接口，未来可能改造 | 字段语义、主体标识、用途、授权、完整性、更新及保留条件 |
| 审计范围 | 六领域能力边界 | 首个合同类型、审查角色、适用地域、试点企业与必审规则 |
| 技术 | Go + Eino 为新建方向 | 具体依赖版本、模型、部署约束和容量目标 |

不将厂商产品手册中的功能视作客户已经开放的接口。每个连接器上线前形成能力清单、字段字典、脱敏响应样本及负责人确认记录。

旧项目可参考不可变文件、证据定位、人工纠正、修改方案、重审、任务恢复和事件设计；现有 API、目录、状态枚举、规则数量与前端布局不自动成为新产品约束。原法律 Skill 只是规则候选来源，其法律依据和适用性须重新确认。

## 3. 分层架构与职责

| 层/模块 | 职责 | 边界 |
|---|---|---|
| 接入与交互 | Web、业务 API、合同节点接口、SSE、对话助手 | 校验身份和请求；不直接形成专业结论 |
| 案件应用服务 | 案件、材料绑定、计划、授权、人工任务、业务命令 | 页面、对话和外部系统走同一命令及权限校验 |
| 持久审计工作流 | 依赖、执行、等待材料、超时、重试、取消、完成门禁 | 唯一业务调度权；不委托模型决定必审项 |
| 文档与共享事实 | 解析、定位、主体归一、事实候选、确认、冲突、快照 | 唯一案件事实视图；按域授权读取 |
| 规范与规则 | 法律知识、企业制度、规则包、适用性、发布和评测 | 规范内容与执行规则有来源映射，权限隔离 |
| 领域执行 | 五域检查及跨域检查，使用规则、计算、模型或 Agent | 只通过应用授权工具读取；输出先作为候选 |
| 决策与报告 | 固定聚合、人工决定、报告、整改与复核 | 报告叙述不能改写结构化结论 |
| 连接与基础设施 | 数据源 Adapter、模型/Eino、数据库、对象存储、观测 | 供应商格式和框架对象不进入领域层 |

依赖方向为 api/worker → application → domain + ports。Adapter 实现 Port；领域层不依赖 Eino、HTTP、数据库或供应商 SDK。

建议工程模块：cases、documents、facts、knowledge、policies、integrations、execution、checks、decisions、collaboration；按实际切片创建，避免先铺六套空 Agent 目录。

Eino 可用于结构化模型调用、受控工具循环和单任务内图编排；业务任务恢复与状态由应用拥有。正式审计不必经过 Main Agent，需要探索的步骤才使用 Agent。领域结果通过验证后落库，再形成业务事件。

## 4. 案件入口、流程主权与合同版本

### 4.1 支持的入口情形

| 情形 | 材料及意见来源 | 流程主系统 | 本平台行为与结果用途 |
|---|---|---|---|
| 用户直接上传、尚未进入合同流程 | 用户文件及声明；上游意见可不存在 | 本平台管理预审案件 | 出预审意见；后续可导出或绑定合同流程，不声称完成正式审批 |
| 已有流程，用户手工发起辅助审查 | 合同 ID + 接口附件；或上传件与源版本比对 | 合同管理系统 | 辅助审查；没有节点调用身份时，不擅自推进原流程 |
| 合同管理系统在审批节点调用 | 指定合同版本、节点、审批轮次、截至该时点的意见 | 合同管理系统 | 创建审计任务，异步返回状态和结构化意见；原系统决定流转 |
| 先在 Agent 预审，后提交/绑定合同系统 | 预审材料 + 后续流程材料 | 绑定后由合同系统管理正式审批 | 版本、规则、权限、数据时效及检查范围一致才可复用；否则增量或全量复审 |
| 用户直接上传，同时查询历史背景 | 用户文件 + 经确认的主体/项目 + 授权历史合同 | 本平台管理本次审计 | 当前材料可独立于流程；历史数据补充背景，不替换上传件 |
| 已审批或签约后的事后复核 | 已签版本、历史意见、最新授权财务/外部数据 | 原系统保留原流程结果 | 新建事后复核运行；注明审计时点，不覆盖过去的审批事实 |

先建设直接上传及只读合同导入两种入口，同时将未来节点身份预留到模型；实际回写和节点推进另作集成切片验收。具体先开放哪种入口由首个试点环境决定，不把整个产品绑定在唯一顺序上。

### 4.2 身份与关联

AuditCase 表示一次业务审查事项，AuditRun 表示在固定材料和规则下的一次执行。ExternalBinding 至少包含：

- tenant_id、source_system_id、external_contract_id；
- external_document_version、workflow_instance_id、node_instance_id、approval_round；
- source_request_id、材料内容哈希、案件用途及流程主系统；
- 上游意见快照 ID、授权主体、回调目标登记 ID。

节点请求按租户、来源系统、源请求 ID 幂等；同请求 ID 携带不同内容必须报冲突。合同号或文件哈希单独不足以去重：同文件在不同审批轮次、规则版本和审计时点可以合法重审。同一文件可有不同权限和用途，不能因哈希相同跨案件泄露结果。

上传件与源附件内容不同，创建新材料版本或分支并明确本次审查对象；不得静默选“最新文件”。报告和回写必须绑定被审版本及本次 AuditRun。

### 4.3 节点调用与回写

推荐接受请求后返回任务标识，再用查询/事件/已登记回调传递业务状态，不让一个 HTTP 请求等待完整模型审查。

契约覆盖：accepted、running、needs_material、completed、failed、cancelled；这些执行状态与建议通过/整改/人工复核等业务结论分开。异步等待是持久状态，不长时间占用模型调用。

源系统撤回、附件变更、重新提交或节点失效时，本次结果标为不再适用于当前流程；新请求触发新运行。回写使用幂等结果 ID 并校验当前源版本及轮次，过期结果不能推进新节点。若对方没有版本比较能力，则回写为带版本标识的参考报告，不自动作审批推进。

回调采用已登记目标、认证/签名、防重放和有限重试；发送记录通过事务 outbox 持久化。读取连接器与写回连接器分权限，首版默认只读；“审计完成”不自动等于“节点批准”。

### 4.4 上游意见的使用

上游意见保留作者/部门、角色、时间、流程节点、针对的文档版本、结论、条件和解决状态。它是意见记录，不自动成为合同事实，也不自动代表具备豁免权限。

法务意见可提示复查方向，财务意见可提示口径，但正式检查仍验证依据。为降低既有意见对独立判断的影响，可先完成基础检查，再比较上游意见与新发现。意见针对旧版本时标为待确认是否仍适用。

## 5. 共享事实：唯一权威视图与来源冲突

### 5.1 本体、规范、规则与事实不是同一类数据

| 类型 | 内容 | 示例 |
|---|---|---|
| 领域本体/语义模型 | 对象、关系、属性及约束 | 法人、集团、合同、付款义务、应收、应付、控制关系 |
| 规范知识 | 法律法规、企业制度及版本化原文 | 某法律某条、集团采购制度某款 |
| 可执行规则 | 在何种条件下检查什么、如何判定、需要什么证据 | 满足指定交易条件时核验授权材料 |
| 案件事实 | 本次审计中实际发生或约定的事项 | 签约主体、付款比例、账面应付余额 |
| 审计判断 | 基于事实和规范形成的结论 | 缺材料、条款风险、需人工复核 |

法律与企业制度是底层规范知识；本体定义这些规范涉及的概念，不等于把全文存起来。首版以强类型 Schema、关系表和字典实现语义模型，不要求引入本体语言或图数据库。

### 5.2 事实结构与真源选择

每个事实至少包含 fact_id、subject_id、predicate、typed_value、单位/币种/税口径、scope、valid_time/as_of、observed_at、source_refs、提取/映射版本、确认状态及版本。候选推断还保存置信度及验证状态。

区分合同约定金额、流程表单金额、财务已确认金额、未结余额、实收实付，它们常常是不同事实而非互相覆盖的同一字段。

按字段定义来源权威策略：合同文字以固定原文证明“约定了什么”；账务余额以指定账套及口径的财务快照证明“记录了什么”；审批状态由指定流程实例证明。人工纠正形成带理由和权限的案件事实新版本，不改写外部账簿或原件。

同一语义字段出现不一致时建立 FactConflict，保留全部候选、证据和处置记录。未解决冲突影响的检查转为不确定或人工任务，不由各 Agent 独立选值。

### 5.3 运行快照与更新

每次运行绑定不可变 FactSetSnapshot 与 InputSnapshot。后续财务查询、补材料或人工确认产生新输入修订和后续运行；旧结果继续绑定原输入。首版采用完整的新运行快照保证简单可靠，之后再实现依赖驱动的局部复用。

共享不等于全域可见：按租户、法人/账套、案件、字段及用途授权；缺权限与数据不存在分开。模型只获得任务所需字段；银行账号等字段可在确定性工具中比较，仅返回匹配结果及受控证据引用。

Evidence 支持原文跨度、表格、JSON Pointer/记录 ID、计算证明、人工确认、规范引用及缺失性证据。固定字符偏移单位、解析器版本和规范化规则，避免 Go 字节、Unicode 字符及前端 UTF-16 索引混用。

## 6. 财务数据能力与审计价值

详细的数据目录、最低字段、权限分档、审计场景及接口验收样例见 [财务系统审计价值数据清单与接入建议](财务系统审计价值数据清单.md)。以下保留总体架构边界，实际对接按具体场景选择能力。

### 6.1 优先争取的数据

下表是对接需求清单，不代表任何客户已开放，也不代表单一财务系统必然拥有全部数据。

| 优先级 | 最小数据能力 | 可支持的审计价值 | 必须说明的限制 |
|---|---|---|---|
| P0 | 本方组织/法人/账套、对方客商编码及统一标识映射 | 将合同签约方与财务往来对象准确匹配 | 客户与供应商可能是两个编码；名称相同不等于同一法人 |
| P0 | 指定双方、账套、币种、截止日的应收/应付未结余额 | 识别既有往来规模、双方同时存在债权债务的情形 | 保留两个方向；不自动抵销，不将账面余额当未来全部义务 |
| P0 | 余额组成或账龄汇总、到期日、逾期金额 | 识别长期未结、回款或付款拖延 | 无到期日只能算账龄，不能直接判逾期 |
| P0（若可提供） | 合同/项目/订单关联号、未结项目 ID | 区分本合同、历史合同和其他业务的往来 | 无可靠关联键时只能做主体级分析 |
| P1 | 预付、预收、保证金、押金、质保金余额及释放条件 | 识别存量资金占用与新合同付款安排叠加 | 是否已包含在应收应付中必须明确，避免重复计数 |
| P1 | 收付款及核销汇总、部分结算、冲销、退款状态 | 核验结算进度、长期未核销及重复支付候选 | 同额付款不等于重复；缺明细不能确认逐笔重复 |
| P1 | 对账状态、争议款、坏账/减值标记 | 识别账款争议及历史履约风险线索 | 会计估计、业务争议和实际违约不是同一判断 |
| P1 | 信用额度、已占用额度、停用/冻结状态 | 核验继续交易是否触及企业信用政策 | 额度定义、共享范围及占用计算须由来源说明 |
| P1 | 授权集团范围内按法人分列的对方往来 | 识别集团累计往来和风险集中 | 不是完整集团时必须明确覆盖率；不得称集团总额 |
| P2 | 发票状态、已开/已收/未开金额及红冲情况 | 合同、开票和结算的一致性与材料缺口 | 不用发票状态直接证明交付或付款 |
| P2 | 收款主体、账户核验结果、账户变更记录 | 核验合同约定收款方与主数据一致性 | 优先返回受控匹配结果，不要求向模型暴露完整账号 |
| P2 | 项目预算/可用额度、采购订单、验收或入库摘要 | 预算、采购和支付条件核验 | 可能属于采购/项目系统，不能假定财务接口提供 |
| P2 | 本合同付款计划及必要范围内的现金安排摘要 | 识别到期支付安排与本交易资金需求 | 不要求开放全公司现金、总账或资金流水 |

### 6.2 最小可用财务切片

首个场景：给定本方法人、合同签约对方、币种和截止日，获取授权往来摘要，判断既有未结/逾期/预付款是否影响本次交易条件。

即便只能开放汇总接口，仍可形成主体级风险提示。报告必须说明“截至某日、某些法人/账套、某种余额口径”，不能把企业账内记录解释为对方整体偿付能力。

精确到合同的余额、账龄、集团聚合分别作为可选能力，不作为所有连接器的强制方法。按能力拆分小接口，例如 CounterpartyBalanceReader、AgingReader、SettlementReader；能力不足返回 unsupported/forbidden，而非零值。

### 6.3 金额与集团口径

金额采用精确十进制及显式舍入规则，保留原币。跨币种展示须使用固定汇率来源、日期和换算策略；不同币种不得直接相加。

集团聚合必须记录成员法人及关系有效时间、授权范围、账套、合并/个别报表口径和去重规则。合并口径与单体数据不重复相加；集团管理视角汇总不改变债权债务的法人归属。对方集团归属也须有独立证据，不因名称相似自动并组。

应收、应付、预付、预收、承诺未入账金额分别展示。新合同金额可能尚未入账，已关联的余额又可能与存量承诺重叠，不能直接“现有余额 + 新合同金额”称总风险敞口。首版用分项展示，只有经业务确认的度量公式才输出派生敞口。抵销或跨主体清偿安排仅产生需进一步核验的候选，不自行作法律或会计处理。

## 7. 合同管理数据与关系审核

### 7.1 数据能力

- 当前合同：外部 ID、版本、正文/附件、主体、项目、金额、币种、期限、合同类型、流程状态。
- 上游意见：按第 4 节保留版本、节点、作者、条件和处置状态。
- 历史合同：按授权主体、项目、类型、时间和状态分页检索，明确包含草稿、终止或作废版本的规则。
- 关系信息：主合同—补充协议、框架—订单、续签/替代、采购—销售、项目配套合同以及变更链。
- 可选履约摘要：交付、验收、索赔、争议和解除状态；不存在接口时明确缺口。

“与这个供应商签订的所有历史合同”必须返回检索范围、分页完成情况、总数（若支持）、截断标记及权限覆盖。只有 Top-K 候选时不能声称检查了全部合同。

### 7.2 关系从哪里来

优先级是：源系统显式关系及其版本 → 授权人员确认 → 稳定业务标识匹配 → 内容召回和模型推断。优先级表示来源可解释性，不免除错误验证。

每条边保存 relation_type、from/to 合同版本、source_refs、method、置信度、验证状态和有效期。同一供应商只表示共同对方，不自动构成上下游合同。推断关系未经确认，不进入需要确定关联的硬性阻断。

首版以关系表实现；关键标识为主体、项目、订单、框架和外部合同 ID。语义检索补充候选召回，不以向量相似度替代业务关联。

### 7.3 典型检查

补充协议与主合同的优先适用条款及变更范围；订单与框架的金额/价格/数量边界；续签与历史未完义务；相同标的重复承诺；明确关联的采购/销售合同之间的交付、验收、付款、责任和保障缺口。金额对比同时匹配产品规格、数量、计价单位、币种和税口径。

## 8. 可扩展接口与通用参考数据源

### 8.1 统一传输封装，保留领域语义

采用 DataSource Registry + CapabilityDescriptor + Connector Adapter + MappingProfile，不要求所有接口都实现同一套财务方法，也不把全平台数据都变成无类型键值对。

CapabilityDescriptor 记录允许操作、查询参数、字段可见性、组织范围、分页/总数能力、时效、限流、费用、保存限制和支持的语义类型。财务/合同数据映射为领域对象；其他数据映射为语义明确的 ReferenceRecord。“未知”仅指设计阶段尚未确定未来接口，不指运行时把未知字段交给模型理解。

流程：授权查询 → 原始响应的允许范围内保存 → 适配器确定性解析与版本化字段映射 → 类型、单位、枚举及完整性校验 → 标准化事实候选/参考记录 → 按检查用途验证 → 固定案件输入 → 审核模型。字段含义和映射在接入开发时根据接口契约确认，模型不参与字段猜测或映射生成；语义未定义、解析失败或校验不通过的数据不提供给模型作为审计输入，而是返回明确的数据缺口或接入错误。

### 8.2 DataEnvelope 最小字段

source_id、connector_version、mapping_version、request_id、query_scope、subject_refs、authorization_scope、source_record_ids、schema_version、as_of、fetched_at、status、completeness、pagination、snapshot_ref/content_hash、retention_policy，以及标准化 payload 或受控引用。原始响应引用用于受控追溯，审核模型仅接收解析校验后的字段和必要来源信息。

状态至少区分 success、empty、unsupported、forbidden、not_found、partial、stale、timeout、error。empty 只表示该次指定查询没有记录，不代表全域没有风险。字段 null、0、缺失和未授权分别处理；金额单位、时区及枚举含义显式映射。

存储与使用遵循来源许可：允许时保存原始快照；不能保存原文时保留允许的引用、摘要或哈希，并明确未来无法完整重放的限制。哈希不能替代可访问证据。

### 8.3 两级使用与安全边界

两个等级均已完成确定性解析且字段语义明确；等级区别在于来源、覆盖范围和时效是否足以支持指定检查，而非模型是否能读懂字段。

参考级：允许检索、展示和辅助解释，附来源及适用限制；因主体关联、覆盖范围或时效等尚不足以支持指定正式检查，不直接参与该检查的关键计算和阻断。

事实级：有明确字段语义、主体匹配、完整性/时效声明和映射测试，可在授权范围内用于正式规则。参考级不得经模型摘要绕过升级校验。

未知 JSON 可含有恶意指令、HTML、超大内容或伪造链接。内容只作为数据处理，不作为系统指令，不执行内嵌脚本，不跟随任意 URL 发起访问；请求目标与参数由登记连接器和应用限制。响应结构漂移、关键字段变化或映射失败时隔离受影响能力，不能静默套用旧映射。

新增数据源的验收单包含：脱敏成功/空/失败样本、字段字典、授权范围、分页与完整性、映射版本、源系统负责人和适用检查清单。首版做具体 Adapter 与可配置字段映射，不提前开发通用低代码 ETL 平台。

## 9. 法律知识库、企业制度与规则包

### 9.1 法律知识库的范围

需要建设可追溯、版本化的规范知识库；民法典、公司法等是否纳入，由合同类型与检查范围决定，同时考虑相关法规、司法解释、行业或地域规范。首版形成“合同类型—检查项—必要依据”覆盖表，不把收集全部法律作为启动前提。

全文用于保存、检索和核对，不默认把所有法律全文放入每次模型上下文。建议：

1. 规则明确绑定必要依据 ID 和版本，执行时必载，不能只依赖相似度检索。
2. 结合合同类型、角色、地域及相关时间筛选，再按条款号/关键词/语义混合检索补充。
3. 以条文为基本单元，同时保留章节、定义、例外、引用条文和必要相邻上下文。
4. 任务需要且长度允许时读取某部法律的全文，作为补充工具能力；不据此省略引用和适用性校验。
5. 报告只引用已登记、可核对的版本化原文；搜索不到必要依据时转人工，不靠模型记忆补法条。

规范记录含正式名称、发布机关、效力类型、条款 ID、发布/施行/失效时间、适用地域、来源链接、内容哈希、版本关系、入库和复核记录。历史时点与新旧法适用可能需要规则或法务判断，不能简单按审计日期取“最新版本”。

更新先形成候选版本、变更比对、受影响规则列表和法务评测；发布后影响新运行，历史快照不改写。旧案件按新规范复核必须显式创建新运行。

官方法律来源可参考国家法律法规数据库；本次未验证其批量下载或 API 能力，不以此假定可自动全量同步。检索服务、转载注释及案例解释的使用范围和授权另行确认。

### 9.2 企业制度

制度原文保留适用组织、部门、业务类型、金额范围、生效区间、审批发布主体及附件。制度间优先级、集团与子公司适用关系、授权例外都须显式建模。仅有上游“同意”意见，不足以证明获得制度豁免。

从制度生成规则属于作者流程：提取候选 → 对照原款 → 补齐适用性和证据条件 → 正反例评测 → 人工审批发布。

### 9.3 统一规则包与受控 Skill

结构化规则包是执行定义的唯一作者源，规范原文是依据源，两者职责不同。包内包括稳定 rule_id、版本、来源映射、适用范围、前置事实、检查策略、风险策略、证据要求、无法判断条件、工具白名单和评测样例。

编辑器修改结构化作者源；SKILL.md/模型 Instruction 是带哈希的派生产物，首版不允许反向独立编辑导致双真源。外来 Skill 导入为候选，必须经过映射和评测。

平台法律包与租户制度包共用发布、审批、快照和校验底座；平台法律包由平台授权负责人发布，企业不能覆盖。复杂算法随执行器代码发布，规则数据与说明独立版本化。首版禁止租户上传任意可执行脚本，工具来自登记能力。

运行必须覆盖固定计划中的每个适用检查项，Skill 按需披露只优化上下文，不能决定哪些必审规则被忽略。

## 10. 领域检查与证据门禁

每个适用检查项均执行：前提/适用性判定 → 读取必要事实与材料 → 确定性检测和必要语义检查 → 候选输出 → 证据及语义验证 → 风险策略 → 持久化。规则检测只提供线索，不能作为进入语义审核的唯一门槛。

存在性证据证明原文/记录存在；缺失性证据记录检查范围、解析覆盖、材料完整性和检查方法；计算证据记录输入、公式、口径及执行器版本。检索没命中不等于全文没有，解析缺页时不能作强缺失判断。

验证分为：来源真实性、版本/归属一致性、引用定位、证据对结论的支持程度。高风险结论必须有足够支持证据，无法确认时输出无法判断或人工复核。模型推理不是证据，模型提出的修订条款明确标为建议，不能伪装成合同原文。

外部核查仍通过登记 Provider 获取主体及相关风险记录。失败/未匹配不等于无风险；记录是否构成本交易禁入条件由适用政策、主体匹配和事实支持共同决定。

探索性检查允许发现固定规则外的问题，但输出候选发现，有预算、证据与人工验证边界，不自动发布新规则或改变正式检查清单。

## 11. 跨域检查与综合审计

### 11.1 显式依赖图

不让五个 Agent 自由互相讨论后投票。把成熟跨域场景定义为 CrossDomainCheck，包含：

- rule_id/version、适用交易场景、required_fact_types、required_result_refs；
- 主体/合同关联要求、数据时间容差、必需权限与材料；
- 确定性度量、语义判断点、反例/例外、证据要求、输出和复核策略。

应用编译事实与检查依赖 DAG。事实齐备后并行执行独立检查；跨域节点只等其实际依赖，不必等待无关领域。正式总报告等待本次所有必审节点达到允许的终态，存在缺口时只能形成受限报告或人工任务。

领域结果暴露必要的 typed_findings、事实/证据引用及不确定性，不只给风险等级和摘要。跨域执行器通过授权工具取必要事实与原文片段，不默认读取全部原始数据，也不局限于摘要。

### 11.2 首批候选场景

| 场景 | 组合输入 | 输出与控制 |
|---|---|---|
| 存量逾期下继续给予宽松付款条件 | 对方应收逾期 + 新合同赊销条件 + 企业信用政策 | 条件不匹配及审批/保障建议；缺到期日不判逾期 |
| 高预付与保障不足 | 存量预付 + 本合同付款安排 + 交付/担保条款 + 经核验外部事实 | 分项资金风险与缺口；不重复累计已入账金额 |
| 项目上下游现金安排错配 | 明确关联的采购/销售合同 + 付款/收款触发条件和金额 | 在明确情景假设下计算时间缺口；不把条件性回款当确定现金 |
| 上游意见尚未落实 | 上游附条件意见 + 其适用版本 + 当前正文/材料 | 已落实、未落实或无法判断；不把审批意见当最终事实 |
| 集团累计业务触及企业授权要求 | 获授权法人分列往来/合同 + 组织关系 + 企业制度 | 仅在制度明确累计口径时判断；覆盖不全提示缺口 |
| 补充协议改变保障但未解决存量义务 | 主补协议关系 + 变更条款 + 未结往来/履约事实 | 指明变更与既有义务冲突，保留完整证据链 |

这些是待业务/法务确认的规则候选，不是现成法律结论或自动禁入规则。

### 11.3 减少漏报、误报与重复计数

固定跨域规则覆盖已知高价值场景；受控语义探索补充组合发现；复杂或高影响判断交人工复核。模型分歧触发证据复查，不按投票数形成真值。

同一基础风险可能被法律、财务和跨域重复引用，使用 risk_instance_id 与来源依赖归并展示；不简单相加权重或重复提高等级。财务义务跨系统重复、合同重复版本也先去重再计算。

金标包括组合正例及消融反例：只改变一个关键前提，结论应按规则改变；例如合同相似但项目不同、应收未到期、审批条件已落实、已存在有效保障。评测跨域检查是否比单域增加有效发现，而非增加文本长度。

### 11.4 增量重审与决策

事实/合同/规则/关系更新后，应用沿依赖图标记受影响结果 stale；冻结旧 DecisionSnapshot，为新运行复用仍有效结果并重算依赖节点。复用须比较输入哈希、执行器/规则版本、权限与时效，不能只按 check_id。

综合策略产生固定建议与约束，再生成说明；缺权限、缺材料、执行失败等覆盖缺口显式展示。人工例外决定记录权限、理由、适用范围和有效期，不抹去原发现。

## 12. 核心模型与持久执行

核心对象：

- AuditCase、ExternalBinding、DocumentVersion、MaterialManifest；
- AuditPlanSnapshot：审查目的/角色、所选领域及必审项、规则包、适用性策略、跨域及聚合策略；
- InputSnapshot / FactSetSnapshot：文档、意见、财务/合同/外部快照、事实修订、时点和覆盖范围；
- AuditRun：计划、输入、知识快照、模型/提示词/执行器/解析器/映射/Eino 版本、预算；
- CheckExecution：检查实例、任务状态、attempt、租约与 fencing token；
- CheckResult / Evidence / ResultDependency；
- DecisionSnapshot、HumanTask、ModificationPlan、IntegrationDelivery。

结果标识使用独立 result_id，并以 tenant/case/run/check_instance/result_version 定位；检查实例含 domain、rule_pack_id/version、rule_id 和被审对象，避免多个企业包或多个合同重复检查 ID 冲突。

执行状态与专业判断分离：任务可 queued/running/waiting/succeeded/failed/cancelled；成功执行的判断可 passed/issue_found/needs_material/undetermined/not_applicable/human_review。可有部分结果，但正式完成必须核验计划覆盖。

任务按至少一次执行设计；结果提交去重、租约 fencing、取消校验和乐观版本控制。结果、任务提交及业务事件在同一事务内；跨系统发送使用 outbox。SSE 使用案件内原子序号和可续传事件，禁止并发 max(sequence)+1 分配。

模型、网络和人工等待不持有长数据库事务。Eino checkpoint 保存执行上下文，应用数据库保存业务真相；checkpoint 格式升级和不可恢复时的重执行路径须验证。仅应用拥有外层任务重试，框架内部局部重试预算计入同一限额。

历史回放区分：展示原证据与输出、重算确定性结果、重新调用模型。前两项可严格校验，模型再生成评估稳定性，不承诺逐字一致。

## 13. 人工协作、修改与权限

案件闭环包括审查、定位、追问、补材料、事实纠正、局部重审、人工决定；修改方案和候选文档作为独立能力分阶段交付。

模型只能生成修改草稿。用户确认后，确定性修改器对固定基准文档应用经过校验的修改，产生新版本；重审后出新报告。原件与原结果保留。首版若只支持 DOCX 确定性修改，PDF/扫描件等明确只给修改建议。

外部节点案件原则上由合同管理系统负责正式文档与审批流转；本平台产生的候选件以新版本回传，不覆盖源文件。由谁接收补材料、谁确认修改在集成契约中确定。

租户、法人/账套、案件、字段、来源记录和工具权限均在应用层校验，不相信模型自报允许工具。外部上下文不扩大用户权限。历史事实有留存不代表当前用户仍有查看权限。

## 14. Eino 技术验证与基础设施

固定实际使用的 Go module、版本、许可证和升级策略。扩展组件按各自模块验证，不假定 eino-ext 下所有集成共享一个发布版本。

Spike 用一个真实结构的业务切片验证：固定合同与事实 → 少量规则 → 一次受控查询 → 校验证据 → 人工等待 → 重启恢复 → 重审 → SSE/报告。无需先搭六个空 SubAgent。

必要验证：目标模型结构化输出、工具权限、超时取消、成本预算、并行依赖、恢复、重复提交、事件持久化、不可变规则加载与观测。Skill Middleware/AgentTool/MCP 只在所选切片需要时验证；不把未使用能力作为启动阻塞条件。

PostgreSQL 保存业务与任务，对象存储保存允许留存的原件/快照/产物。按实际检索需求增加全文/向量索引；索引不是规范和事实真源。若长流程、复杂定时及运维需求超过任务表能力，再比较专用工作流引擎。

## 15. 分阶段建设与验收

按业务切片估算工作，不沿用旧项目 18～31 周作为承诺。首个试点范围、数据权限、材料格式、连接器与作者能力确定后，再由负责人给出时间与资源预算。

| 阶段 | 主要交付 | 退出条件 |
|---|---|---|
| Phase 0 定界与样本 | 首个合同类型/角色、接口能力与样本、入口责任矩阵、初始本体与规范目录、金标、Eino 切片 | 能解释可审/不可审范围；关键数据来源和负责人明确；技术风险有证据 |
| Phase 1 首个案件闭环 | 直接上传/只读导入的首个入口、固定事实和计划、法律+少量企业检查、证据、复核和报告 | 独立金标达到约定门禁；缺失性证据、权限、恢复与覆盖验证通过 |
| Phase 2 真实数据价值 | 一个财务往来摘要接口、合同历史/关系读取、首批跨域规则 | 真实授权样本上的主体、余额、时间口径及关系验证通过；受限报告可解释 |
| Phase 3 流程与重审 | 合同系统节点接入、上游意见、版本绑定、异步回写、补材料和依赖重审 | 重复/乱序/撤回/换版本/回调失败场景通过；不推进错误节点 |
| Phase 4 治理与扩域 | 制度作者界面、审批评测、更多规则、外部核查及参考数据映射 | 来源与发布治理完整；新领域金标、映射漂移与租户隔离通过 |
| Phase 5 试点上线 | 完整操作链、容量/成本、备份恢复、告警、运行手册、业务签署 | 新产品上线门禁通过；形成支持与规则维护责任 |

若试点只能由合同节点触发，将 Phase 3 的最小节点接入前移；接口权限和样本确认始终从 Phase 0 开始。综合策略从 Phase 1 存在，跨域规则从 Phase 2 加入，不能拖到最终阶段。修改候选文档根据首个客户需求进入明确阶段，不以“保留旧前端”默认完成。

金标由领域负责人标注，开发集和独立验收集分离。至少 20 份脱敏合同仅作为种子，不作为六域生产充分性依据；按合同类型、角色、规则、缺材料、反例与组合风险覆盖确定规模。

验收度量：高风险漏报、误报、必审覆盖、证据支持度、不确定判断的恰当性、主体误匹配、跨域新增有效发现、运行稳定性、成本与延迟。具体阈值和样本要求在 Phase 0 签署，不写未定义的“达到阈值”。

上线使用新产品试点和版本发布策略，不涉及旧 Python 系统迁移/退役。应用回滚不得抹去已生成事实、结果或人工决定；外部节点可按预先约定进入人工处置，不能故障时静默当作通过。

## 16. 下一步交付清单

1. 明确首个客户的合同类型、审查角色及预审/流程节点目的。
2. 获取一份财务往来接口、一份当前合同/意见接口、一份历史合同查询的脱敏样本；未提供能力标为未知。
3. 建立能力—字段—语义—权限—可支持检查矩阵；优先验证本方/对方主体映射、余额口径和源文档版本。
4. 定义 AuditCase、ExternalBinding、InputSnapshot、Fact、Evidence、CrossDomainCheck 和 DecisionSnapshot 的首版契约。
5. 选取少量法律、企业及跨域规则形成来源—规则—正反例映射，法务/财务共同确认。
6. 确定规范目录与引用版本策略，不先做全法律数据采集工程。
7. 完成实际 Eino 切片及重启、重复提交、材料变化验证。
8. 将阶段拆为含负责人、依赖、验收标准和明确范围的 backlog，再给工期。
