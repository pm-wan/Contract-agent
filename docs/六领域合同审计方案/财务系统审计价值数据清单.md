# 财务系统审计价值数据清单与接入建议

> 版本：v0.1
> 日期：2026-09-16
> 状态：需求与语义设计；客户实际接口能力待确认
> 上位方案：[六领域合同审计平台从零建设实施计划](Go后端重构与六领域审计实施计划.md)
> 当前实施顺序和技术架构以 [Python 全栈实施计划](../development/00-project/实施计划与里程碑.md) 为准；真实财务 API 的详细设计安排在 MVP 后半段。
> 目的：为财务负责人、接口负责人和产品研发共同确定“取什么数据、支持什么检查、开放到什么粒度”提供依据。下列字段是本平台需求，不是用友/金蝶现成接口承诺。

## 1. 业务目标与取数边界

财务域首先支持合同签署、续签和变更时的交易条件审查，并为履约期复核提供可选能力。暂不建设全量财务审计、自动记账、付款审批或全公司财务分析平台。

围绕六个问题组织数据：

1. 合同本方、对方在财务系统中对应谁，哪些法人和账套被授权？
2. 指定双方尚有哪些未结往来，方向、性质、期限和金额是什么？
3. 历史结算表现及争议对本次交易条件有什么影响？
4. 当前合同、项目、订单与存量款项能否可靠关联？
5. 新付款、担保、信用和结算安排是否与存量情况及企业政策相容？
6. 数据覆盖、核销与更新时间是否足以支持该判断？

所有查询由应用限定主体、组织、时间、字段和用途。原始 JSON 经接入适配器确定性解析、映射和校验后，形成标准化信息；模型只分析业务，不猜测字段、金额单位或状态含义。

## 2. 先区分往来方向与审查视角

| 标准化方向/性质 | 从本方法人看意味着什么 | 主要审查用途 | 不能直接推出 |
|---|---|---|---|
| 应收 | 账内记录的对方应向本方结算的款项 | 销售赊销、继续授信、催收和续约条件 | 对方整体资信差、全部债务或已构成法律违约 |
| 应付 | 账内记录的本方应向对方结算的款项 | 本方付款义务、供应合作、续签和争议处置 | 对方付款能力差 |
| 预付 | 本方已预先付出的款项及其未核销余额 | 采购预付、追加预付和未完成交易核验 | 未核销就等于供应商未交货 |
| 预收 | 本方已预先收到的款项及其未核销余额 | 本方待履行事项与退款/结算安排 | 已确认收入、全部履约完成 |
| 其他应收/应付 | 来源系统中另行分类的往来款 | 保证金、押金、代垫等指定业务检查 | 所有项目都与本次合同有关 |
| 票据及其他非现金结算 | 以票据或其他方式记录的结算 | 兑现期限、实际现金时点、方式一致性 | 已收到现金、没有后续风险 |

“财务逾期”首先表示超过来源系统记录的到期日；合同违约判断仍需合同条件、有效变更及履约事实。正式输出区分账龄偏长、记录逾期、存在争议和经验证的合同问题。

## 3. 优先级与数据总目录

P0：首个往来审计切片必须明确其可用性；拿不到时缩小报告范围。
P1：按首个客户风险场景选取，明显增强判断质量。
P2：专项或后续能力；不作为首版全量开放前提。

| 数据集 ID | 优先级 | 数据集 | 最小业务粒度 | 审计价值 |
|---|---|---|---|---|
| FIN-01 | P0 | 组织、法人、账套及对方身份映射 | 本方法人 × 对方法人 × 源系统编码 | 确认审的是谁、数据属于谁 |
| FIN-02 | P0 | 往来余额与性质分项 | 双方 × 币种 × 截止日 × 款项性质 | 识别现存未结规模 |
| FIN-03 | P0 | 账龄/到期/逾期分布 | 同口径余额的分桶或分期未结项目 | 区分长期挂账和到期拖延 |
| FIN-04 | P0，允许缺失降级 | 合同、项目、订单关联 | 余额/单据行/结算分配与业务对象的映射 | 主体级分析提升为合同级核验 |
| FIN-05 | P1；高预付采购场景前移 | 预付预收、保证金、押金、质保金 | 双方 × 类型 × 关联业务 × 截止日 | 判断资金占用与新条款是否叠加 |
| FIN-06 | P1 | 收付款执行、核销、退款与冲销 | 结算事件及其分配 | 区分已支付、未核销和重复候选 |
| FIN-07 | P1 | 历史结算行为 | 指定观察期的未结及已结项目 | 识别结算拖延趋势 |
| FIN-08 | P1 | 对账、争议、催收、减值标记 | 争议事项/对账批次/指定款项 | 区分真实拖欠、对账差异和估计信号 |
| FIN-09 | P1 | 信用政策与额度 | 额度池 × 组织/客商 × 有效期 | 核验新交易的企业信用约束 |
| FIN-10 | P1，派生视图 | 授权集团分法人往来 | 法人分项及其来源 | 避免子公司局部视角遗漏 |
| FIN-11 | P1；票据结算场景必需 | 票据及非现金结算状态 | 票据/结算工具及关联分配 | 区分结算记录与现金兑现 |
| FIN-12 | P2；收款方变更场景前移 | 收款主体、账户核验及变更 | 指定账户的核验结果 | 发现收款安排不一致 |
| FIN-13 | P2 | 开票、收票、红冲及关联 | 发票行/业务分配或合同汇总 | 核验开票、支付条件和资料闭环 |
| FIN-14 | P2 | 未入账承诺、预算与支付计划 | 合同/订单/项目的指定额度 | 补充账面余额之外的义务视图 |
| FIN-15 | P2 | 交付、验收、退货及保障摘要 | 关联义务/业务单据 | 支持付款前提及保障检查 |
| FIN-16 | P0，贯穿全部 | 数据口径、覆盖、时效和质量 | 每次响应/快照 | 防止把缺数据解释成无风险 |

## 4. 各数据集的字段与使用条件

### FIN-01 主体与范围

最低字段：本方法人 ID/名称、结算组织 ID、账套/账簿 ID、对方客户编码和供应商编码、统一主体标识（若有）、编码所属源系统、映射状态、授权范围。

增强字段：财务组织与法律主体的对应关系、收款/付款组织、组织关系生效区间、客商更名/合并/停用记录、代收代付关系及来源。

一个对方法人可以同时有客户和供应商编码；不同账套也可有不同编码。结算组织、采购组织和法律签约方不必相同。没有稳定标识时由授权人员确认映射，保留证据；不能仅以名称相似自动合并。

输出应说明实际使用哪些本方法人和对方编码。集团成员关系可由组织主数据服务提供，不强制要求财务接口独立维护完整集团树。

### FIN-02 往来余额

最低字段：主体与账套、截止日、币种、款项方向/性质、未结金额、余额定义、单据状态过滤、源汇总记录或快照标识。

增强字段：期初余额、期间新增、期间结算/调整、期末余额；业务应付/暂估/财务口径分类；原币和本位币金额、汇率日期；零余额与不存在记录的区别。

不统一假定某会计科目编码在所有客户中表达同一业务。映射需财务负责人确认；账面价值、减值后净额、未核销原额不能混用。借贷方向、负数、红字和预付款包含关系显式处理。

余额汇总只支持往来规模分析。若要解释形成原因，必须补充组成项目或来源系统已计算的分类，不由模型编造。

### FIN-03 账龄、到期与逾期

最低字段：余额口径 ID、as_of、aging_basis（业务日期/到期日/其他已定义基准）、分桶边界、各桶未结金额、日期缺失金额、完整性。

有明细时补充：未结项目/分期 ID、业务日期、有效到期日、未结金额、到期日来源、变更版本、宽限期定义、争议标记。

同一应付单可能分多期到期，必须按分期余额判定；不能拿最早到期日计算整张单据的逾期。合同约定“验收后若干天”但验收事实缺失时，不自行生成确定到期日。

优先采用来源已核验的到期摘要。自行计算时固定时区、审计日期、到期日当天是否算逾期的约定、规则版本和例外；账龄桶和逾期桶必须区分。金蝶官方账龄说明明确支持不同日期基准及未审核单据选项，说明口径必须随数据传递。[官方说明](https://open.kingdee.com/k3cloud/help/AR_AGINGANALYSIS.html)

### FIN-04 业务关联

最低字段：源单据 ID/行 ID、外部合同 ID/号、项目/订单 ID（可分别缺失）、关联方式和确认状态。

增强字段：合同版本/补充协议、付款期次、分配金额/比例、原分配和冲销引用、关联创建及变更时间。

金额在一张收付款单上覆盖多个合同，或一张合同对应多张财务单据，都必须通过分配关系表达。没有分配金额时，不能把整单余额分别计入每个合同。只存在备注中的合同号可以作为候选，适配器按已确定规则提取后仍要验证关联，不能直接当成确认分配。

接口无关联能力时不阻止主体级审计，但报告必须写“无法归属到当前合同”，不按金额/日期巧合强行归属。

### FIN-05 预付预收及保障类往来

最低字段：方向、业务类型、余额、币种、形成日期、关联主体；是否已计入 FIN-02 的定义。

增强字段：合同/订单分配、原始金额、已核销/退款/结转金额、预计结算时间、约定退还/释放条件、应释放与实际释放状态、来源凭据。

保证金、押金、质保金分别记录性质和方向，不能统称预付款；保函/保险不是同一种账内金额，应另作保障引用。未核销预付只能提示核验交付、结算或退款，不直接证明未交付。

新预付风险检查需要结合合同付款安排与履约/保障信息，不能用预付余额单独否决交易。

### FIN-06 收付款与核销

最低字段：事件 ID、业务类型、主体、币种、金额、执行状态、业务/执行时间、结算方式、源单据关联。

增强字段：申请/审批/执行/银行确认状态及各自时间、关联应收应付分期、核销金额和生效日、未分配金额、退款/冲销/撤销引用、支付业务唯一标识、账户核验引用。

区分：付款已审批、付款指令已发出、系统记录已支付、银行确认成功；没有银行确认能力时只能报告来源系统记录的状态。

核销可能涉及收款、退款、正负单或其他已配置结算关系，不能直接等同现金到账。金蝶官方核销方案列出了多种核销关系，因此必须保留核销类型及关联来源。[官方说明](https://open.kingdee.com/K3Cloud/help/AR_MATCHSCHEME.html)

重复支付检查先排除重复接口记录、部分支付、分期、批量分配、重试、冲销和退款，再产生待复核候选。没有业务关联及执行证据，只能识别相似记录，不能确认重复付款。

### FIN-07 历史行为

最低字段：观察期起止、统计基准、已结与未结项目数/金额、数据完整性、到期信息覆盖情况。

增强字段：分期有效到期日与结算分配日、拖延天数分布、延期批准记录、逾期金额趋势、争议单独分组、最近对账时间。

仅分析已结清单据会遗漏仍未结的高风险项目，因此同时展示已结表现与未结分布。观察期、样本量与分母必须明确，不能将少量记录概括为长期稳定表现。

供应商场景的本方历史付款拖延，不作为供应商信用差的依据；可提示续约时需要厘清争议或改善付款安排。对方交付表现需要采购/验收数据支持。

### FIN-08 对账与争议

最低字段：事项 ID、关联主体/款项、状态、截至时间和来源。

增强字段：争议金额、原因类别、对账差额、最后确认时间、双方确认情况、未决事项、减值/坏账估计标记和依据引用、实际核销类型。

对账确认不等于到账；有催收不等于已认定违约；计提减值不等于债权已消灭。将这些数据作为不同信号，具体影响由规则及合同事实判断。

争议细节敏感时可只提供类别、金额、状态、负责部门和受控证据引用，不要求开放全部内部沟通。

### FIN-09 信用额度与政策

最低字段：额度池 ID、授权组织、适用客商/集团范围、币种、限额、已占用、可用额、有效期、计算时点和状态。

增强字段：额度共享关系、临时额度、冻结原因类别、授信账期、额度占用组成、担保覆盖条件、人工例外及有效期。

优先使用来源计算的可用额并保存其口径，不能默认限额减应收等于可用额；订单、出货、票据等是否占用由客户定义。同一共享额度池在多个组织展示时不能相加。

字段来自信用管理或销售系统时通过对应连接器获取。没有企业明确政策和额度定义，仅输出数据，不自行发明通用阈值。

### FIN-10 集团视角

这是 FIN-01/02/03/05 等数据在授权范围内的派生视图，不单独要求财务系统提供一个不可解释的“集团风险总分”。

最低字段：集团引用、本方法人成员清单与有效期、已覆盖法人、未知/未授权范围标记、各法人账套与各币种分项、聚合策略及来源。

同一法人多套账簿需确定是否为不同核算视角，不能重复累计；合并报表与成员账簿不叠加。集团范围不完整时显示“已授权范围汇总”，缺少集团全量分母时不计算覆盖百分比。

本方集团与对方集团分开标识。对方的母子公司可能是不同债务人；风险展示可关联观察，不能自动互抵或转移履约义务。集团总敞口需要明确去重和业务公式，首版不生成。

### FIN-11 票据与非现金结算

最低字段：工具/票据 ID、类型、金额、币种、到期日、来源状态、关联往来和分配、状态时点。

增强字段：出票人/承兑人/交易对方区分、贴现/背书/退回/到期收款事件、未兑现金额及与应收余额的包含关系、来源明确的追索或担保属性。

如果应收被票据结算，不能将应收减少解释为等额现金回款；工具金额也不能再无条件叠加到原余额。金蝶官方说明将到期收款、背书、贴现和退票作为不同后续处理，支持对此单独建模。[官方说明](https://open.kingdee.com/k3cloud/help/CA_341.html)

供应链金融凭证、保理等仅在客户确有场景且接口定义明确时接入，先保留业务状态及证据，不由模型猜测其法律或会计后果。

### FIN-12 收款方与账户

最低字段：被核验合同版本/收款安排、本方/对方主体、查询账户受控标识、匹配/不匹配/未知、核验来源及时间。

增强字段：源主数据版本、历史变更时间、变更审批状态、授权代收关系及有效期、原/新账户指纹。

优先在受控工具中完成账户比较，给模型核验结果和必要引用。与主数据一致只能证明一致性，不能宣称银行账户真实有效或无欺诈风险；需要银行核验的场景另取对应能力。

### FIN-13 发票

最低字段：发票/票据业务记录 ID、购销双方、币种、金额及含税口径、日期、来源状态、合同或应付关联（若有）。

增强字段：原票与红冲关系、分配金额、收票/开票/认证/核验状态的独立定义、开票条件依据、未开票/未收票摘要。

用于资料一致性和已明确开票条件的检查。开票不证明交付，认证不证明付款；无开票时间条件时不能仅凭未开票判违规。发票全票金额跨多合同使用时也须分配。

### FIN-14 未入账承诺、预算与计划

最低字段：合同/订单/项目标识、金额口径、已执行与剩余承诺、批准状态、预算/额度池、有效期和更新时间。

增强字段：撤销/变更承诺、在途付款、占用/释放关系、条件性付款计划、不同情景和已入账项目关联。

数据可能位于采购、预算、项目或资金模块，不假定通用应收应付接口能提供。金额不能与已入账余额直接相加；本平台仅按经确认的重叠识别和度量公式形成衍生分析。

一期不索取全公司总账、账户现金余额或完整资金计划。若客户只开放当前项目“额度是否足够”，也可用于对应检查，结果保留校验时点和额度范围，不解释成全部预算充分。

### FIN-15 履约与保障

最低字段：与合同/订单的关联、业务事项、状态、发生时间、确认主体和证据引用。

增强字段：验收金额/数量、部分验收、退货、争议、保障金额/期限/受益主体、释放条件。

这类数据可能不在财务系统；财务仅有摘要时要说明间接来源。无履约数据时，对预付未核销、质保金未释放等只提出核验事项，不能下履约定论。

### FIN-16 口径与质量

每次响应必须说明：source_system、connector/mapping_version、request/snapshot_id、authorization_scope、query_scope、as_of、fetched_at、时区、币种/单位、source_record_refs、status、completeness、pagination、已知遗漏与质量标记。

还需确认：

- 有效、已审核、已过账、暂存、作废单据的包含规则；
- 原币/本位币、减值前后、应付/暂估、内部往来的口径；
- 核销状态是否已更新，有无历史补录/反核销；
- 是否支持指定历史截止日，还是只能提供当前余额；
- 分页期间能否固定快照或水位，是否存在漏页与重复；
- 系统同步延迟、最近结账日和业务日期不是同一个时间；
- 字段未提供、未授权、无记录和金额为零分别表达。

返回不完整时仍可展示已获取事实，但不作依赖全量的否定判断或总量计算。汇总与明细来自不同时点时不能强行对账。刷新产生新快照，历史报告不静默更新。

## 5. 首批建议实现的审计场景

| 检查 ID | 场景 | 必要财务数据 | 额外依据 | 数据不足时 |
|---|---|---|---|---|
| FC-01 | 对方已有逾期应收，新合同继续给予赊销 | 01/02/03，必要时 09 | 新合同条件、企业信用政策 | 无到期日只报告未结与账龄，不判逾期 |
| FC-02 | 存量预付仍未结，又约定较高新增预付 | 01/05，关联用 04 | 新合同、保障与履约材料 | 提示占用与待核验事项，不断言未交货 |
| FC-03 | 本方已有到期应付，续签仍依赖持续供货 | 01/02/03/08 | 续签条件、争议/付款安排 | 报告本方结算问题，不归为对方信用差 |
| FC-04 | 合同约定收款方/账户发生变化 | 01/12 | 当前合同、授权代收和变更材料 | 输出未知并要求核验 |
| FC-05 | 结算金额与当前合同或付款期次不一致 | 04/06，必要时 13 | 合同版本、分期、退款和变更 | 无分配关系时只识别主体级线索 |
| FC-06 | 相同业务疑似重复付款 | 04/06 | 支付标识、分期及业务依据 | 无明细不执行逐笔重复判断 |
| FC-07 | 新交易可能触及企业额度 | 09，必要时 10/14 | 明确占用政策、新合同情景 | 不以应收余额替代信用占用 |
| FC-08 | 票据结算与合同现金付款条件存在差异 | 06/11 | 合同结算方式及有效变更 | 无工具状态不声称已收现金 |
| FC-09 | 上下游收付款时间存在缺口 | 04/14，必要时 02/06 | 明确关联合同、履约触发条件 | 仅作带假设的情景分析，不给确定现金预测 |
| FC-10 | 合同变更/终止后存量往来待处理 | 02/04/05/06 | 主补协议或终止安排、履约事实 | 形成清算/确认材料清单，不直接判应退金额 |

上述检查输出“事实 → 与当前交易的关系 → 适用规则 → 证据 → 建议动作”。没有适用规则时可提示关注事项，但不得伪造违规阈值。

## 6. 有条件才计算的指标

所有指标固定输入快照、主体、币种、日期基准和公式版本。以下是平台建议定义，须与客户统计口径确认，不冒充厂商默认算法。

| 指标 | 定义条件与计算 | 禁止的简化 |
|---|---|---|
| 已知逾期未结金额 | 在未结分期中，按确认的到期规则筛出逾期项再求和；另列到期日未知金额 | 将全部长账龄余额当逾期 |
| 到期信息覆盖率 | 同范围同币种中具有有效到期信息的未结金额 / 相应未结总额；负数/红字先按口径独立处理 | 未知金额忽略后声称覆盖全部 |
| 已知到期项目中的逾期占比 | 逾期未结 / 到期信息已知的未结；分母为零时不可计算 | 分母不是全部未结却称“总体逾期率” |
| 历史支付拖延分布 | 按各已执行分配的到期与实际结算日期统计，并同时展示未结分布 | 用平均值掩盖未结款；只统计已结项 |
| 合同已结算金额 | 根据经验证业务分配、有效状态及退款冲销净调整，保留现金/非现金分类 | 直接把合同关联单据表头全额相加 |
| 授权集团分项汇总 | 对已确认独立的法人/账套及同币种分项聚合，保留成员明细 | 重复累计多账簿、共享额度或合并报表 |
| 近期确定应付安排 | 只汇总已确认触发且有明确到期日的分期；条件性项目另作情景 | 将所有未来合同金额称近期应付 |
| 往来集中程度 | 仅在授权同口径总体分母可用时计算，注明是余额集中而非收入/采购占比 | 只有单个对方数据却推测整体集中度 |

来源系统可提供口径明确的汇总指标时，可以使用该指标，不必要求所有明细。没有足够字段就不计算，不由模型补齐。每类指标同时返回 coverage 和 limitations。

## 7. 权限有限时的四档交付

| 档位 | 对方可以提供 | 本平台可以交付 | 不承诺 |
|---|---|---|---|
| L0 | 指定条件的核验结果、时点和来源引用 | 是否存在某类记录、政策条件是否满足的有限结论 | 自行复算金额、列全量明细 |
| L1（首版推荐） | 指定双方往来摘要，币种、截止日、余额分项和明确口径的分桶 | 主体级未结/逾期/预付画像，与新条款组合分析 | 精确归属当前合同、逐笔重复判断 |
| L2 | 未结分期、结算摘要和可靠合同/项目分配 | 合同级结算进度、到期与变更核验 | 完整付款取证、全集团分析 |
| L3 | 授权范围内结算事件、核销关系、历史与证据 | 重复候选、行为趋势及更强可解释性 | 超出已授权范围的整体财务结论 |

四档可按能力混合，不要求整体升级：例如余额只有汇总，账户核验只有布尔结果，指定合同却允许提供明细。对方源端生成受限摘要 API 是可行方案；“财务系统不开放明细”不等于财务域没有价值。

## 8. 第一轮接口沟通清单

### 8.1 优先争取五类只读能力

1. 主体映射：本方签约法人、账套、对方客商编码的对应与授权范围。
2. 往来摘要：指定双方、币种、截止日的应收/应付及预付/预收分项。
3. 到期摘要：同口径未结项目的日期基准、账龄/逾期分桶、未知金额。
4. 业务关联：当前合同/项目对应哪些往来项目，关联是否可验证。
5. 质量说明：快照时间、单据过滤、完整性、核销及同步限制。

这五类是语义能力，可以由一个聚合接口提供，也可以来自多个读接口或受控导出，不预设五个 URL。预算、完整流水、发票和集团总账不作为首轮统一必需项。

### 8.2 财务负责人需确认

- 本次最优先是采购、销售、续签还是变更场景？哪些往来性质影响决策？
- 有效余额与逾期分别采用什么规则，哪些单据和未审核数据被排除？
- 预付/票据/保证金等是否已包含在主余额中？
- 客户与供应商编码能否映射同一法人，集团到底开放哪些主体？
- 核销与实际支付相差多长时间？业务争议、减值、退款如何表达？
- 什么情况下需要人工核验，哪些企业政策能形成正式限制？
- 是否支持历史截止日及来源证据保存，源数据更新后如何解释旧报告？

### 8.3 接口负责人需提供

产品与版本、模块、授权读操作、字段字典、成功/空/错误/部分响应样本、账套范围、分页/快照方式、限流、返回量、超时、更新时间、历史查询能力、记录引用及保存约束。

字段映射由接入开发人员依据契约确定并通过样例校验；审批发布后运行。结构漂移或关键字段含义变化时暂停受影响能力，不让模型临场解析未知语义。

## 9. 验收样例与数据质量门禁

| 样例 | 预期行为 |
|---|---|
| 同一法人有客户/供应商两套编码 | 可统一主体观察，但应收应付方向保留 |
| 名称相似却是不同法人 | 不合并，不跨主体累计 |
| 本方欠供应商逾期款 | 指明本方结算问题，不判供应商信用差 |
| 业务日期很早，到期日仍未到 | 可报告账龄，不报告逾期 |
| 一单多期，仅首期到期 | 仅按首期未结金额识别逾期 |
| 已付但尚未核销 | 同时显示状态差异，不确认仍欠同额现金 |
| 已核销但结算方式为票据 | 不说现金全部到账 |
| 预付款已包含在原应付并已核销 | 不在余额/敞口中重复累计 |
| 一笔结算关联多个合同 | 按确认分配计算；缺分配时不向各合同计全额 |
| 退款、冲销、反核销和重复响应 | 保留事件关系并去重，不误判重复支付 |
| 零余额、无记录、无权限、缺字段 | 四种情况明确区分 |
| 只查到部分集团法人或部分分页 | 标记受限，不能称集团全部或全量不存在 |
| 两次接口返回不同截止时点 | 不拼成一个未注明差异的统一快照 |
| 只有当前余额却请求历史审查 | 不把当前数冒充历史数，缩小结论或补数据 |
| 共享额度在多组织重复展示 | 按额度池去重，不直接汇总 |
| 币种、金额单位或日期基准缺失 | 阻止受影响计算并返回具体缺口 |

上线前在同一口径及截止时点下，由财务人员将接口数据与源报表/可核验记录抽样对照。金额精度、舍入和允许差异原因明确记录；不能只验证 JSON Schema 合法就宣布财务数据可信。

## 10. 首版推荐范围与后续迭代

第一版目标：在一个试点企业、明确本方法人与对方、有限币种和已授权账套范围内，形成“往来余额 + 到期/账龄 + 预付款 + 数据限制”的画像，并结合当前合同输出少量可复核发现。

建议先完成 FIN-01/02/03/16，按可用性加入 FIN-04/05；选择 FC-01、FC-02 或 FC-03 中与客户真实交易方向匹配的场景。不同时承诺采购、销售、票据、集团信用和逐笔支付审计全部能力。

随后按实际问题扩展：关联不清优先 FIN-04；核销差异突出优先 FIN-06；集团视角重要优先 FIN-10；票据业务重要则 FIN-11 前移。FIN-07 的行为统计在观察期与样本覆盖合适后建设。

每个检查实例明确数据依赖；可选能力缺失只影响相关检查。案件计划强制要求的能力不可用时，输出缺材料/人工复核，不能悄悄跳过并给出通过结论。
