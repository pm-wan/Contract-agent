# 法律域 Skill 与槽位驱动审计设计

> 版本：v0.1  
> 日期：2026-09-16  
> 性质：六领域合同审计平台的法律域与统一执行机制专题设计  
> 适用范围：从零建设的新项目；当前仓库代码和现有 Skill 仅作经验与规则候选来源，不构成兼容或迁移约束

## 1. 文档目标

本文档整理当前关于法律审核 Skill、结构化规则包、关键检查槽位、受控 ReAct 循环及六领域统一执行模型的讨论结果。

核心结论是：

> Skill 不应只作为一段上下文注入提示词，也不应由 Agent 自由决定检查范围和完成状态。结构化规则包应该定义必须执行的检查及必须填充的槽位，AuditPlanSnapshot 固定本次运行的检查契约，持久工作流根据槽位缺口调度确定性执行器、模型、工具、Agent 和人工任务，直到所有关键槽位进入可验证的业务终态。

## 2. 与六领域总体方案的关系

本设计延续六领域方案已经确定的原则：

1. AuditCase 是业务中心，AuditRun 是固定输入、规则、知识和执行版本下的一次运行。
2. 正式审计由 AuditPlanSnapshot 和持久工作流驱动，Agent 不能跳过必审项或决定最终阻断。
3. 共享事实层提供唯一、固定、可追溯的案件事实视图；不同来源的冲突显式保留。
4. 法律规范、企业制度、可执行规则、案件事实和审计判断分层管理。
5. 确定性计算负责金额、期限、阈值、权限和聚合约束；模型负责语义判断、解释、材料缺口和文字表达。
6. 模型推理不是证据；正式结论必须回到可核验的原文、记录、计算、人工确认或规范引用。
7. 执行失败、数据不足、无法判断和专业不通过是不同的状态。
8. 六个领域是产品能力边界，不强制对应六个 Agent。

槽位驱动执行模型是对“固定计划、共享事实、证据门禁、持久工作流和固定聚合策略”的进一步具象化。

## 3. 现有法律与合同 Skill 的经验取舍

现有 Skill 不作为新项目的运行时依赖，只用于提取规则候选、工作方法和反模式。

### 3.1 可保留的经验

#### 可回溯的证据约束

当前 `contract-review` 中以下原则适合作为新系统基础：

- 结论必须引用可定位的原文或数据证据；
- 未找到条款不等于通过；
- 证据不足时显式返回补材料、无法判断或人工复核；
- 不判断签名、印章、证照或外部记录的真实性，只在获得的证据范围内形成结论；
- 不以模型自由答案代替人工最终法律判断。

#### 商业法务工作方法

`claude-for-legal-ZH` 中以下方法值得吸收：

- 先确认合同类型、我方交易角色、法域和交易金额；
- 将合同条款与企业审查指引比较；
- 区分标准立场、可接受让步、不可接受条件和审批权限；
- 对偏离项提供精确原文、影响、候选修订和上报路由；
- 将 SaaS、NDA、数据处理和修订历史作为专项规则层叠加；
- 修订建议优先采用能达到审查立场的最小编辑；
- 超过权限的问题进入明确的人工审批，不由模型自行批准。

#### 报告与可理解性

`ai-legal-claude` 中的条款分类、缺失保护识别、义务与期限提取、通俗解释、谈判优先级和风险面板可用于产品表达层和规则候选库。

#### 确定性候选召回

关键词、正则和轻量文本检测可用于召回原文候选、识别空白项或提示需要执行某项检查，但不能直接产生正式法律结论。

### 3.2 不应继承的模式

- 把整个 Skill 仅作为长提示词一次性注入；
- 让自由 Agent 决定哪些项目应当检查；
- 让多个 Agent 通过投票或固定权重产生“合同安全分”；
- 将 Markdown 报告视为唯一或权威结果；
- 使用模型记忆中的法条、金额阈值或时效信息形成正式依据；
- 把正则命中、搜索未命中或一段模型推理直接当作证据；
- 让租户上传任意可执行脚本；
- 在缺少材料、数据或权限时默认为“未发现风险”；
- 让模型自行选择冲突事实或决定最终流程结论。

## 4. 分层作者模型

新项目应将“知识、规则、Skill、计划和结果”分层建模。

### 4.1 规范知识

保存版本化法律法规、司法解释、企业制度和其他规范原文，包含效力类型、发布与施行时间、失效时间、适用地域、版本关系、内容哈希和复核记录。

规范原文是依据源，不直接决定怎么执行检查。

### 4.2 结构化规则包

结构化规则包是执行定义的唯一作者源，定义：

- 稳定的 rule_id 和版本；
- 所属领域与规则包；
- 适用场景、合同类型、交易角色、组织、金额、法域和时间条件；
- 前置事实和数据覆盖要求；
- 必填槽位及其依赖；
- 确定性检查、语义判断点、反例和例外；
- 绑定的规范依据及版本；
- 证据要求和无法判断条件；
- 风险下限、人工复核和上报策略；
- 允许的工具和执行预算；
- 正例、反例、缺材料和边界评测样例。

### 4.3 Skill 与执行说明

Skill 是由规则和执行配置生成或绑定的受控执行说明，它负责：

- 告诉模型如何完成特定语义任务；
- 解释可用工具的输入输出和使用边界；
- 要求输出结构化候选槽位；
- 区分原文、事实、规范、模型判断和修订建议；
- 正确表达不确定、缺材料和工具失败；
- 禁止越权扩展检查范围、工具权限或最终流程结论。

Skill 不负责：

- 决定本次运行必须执行哪些检查；
- 删除或跳过关键槽位；
- 在冲突事实中自行选值；
- 批准制度例外或越过人工权限；
- 决定案件最终通过、整改或阻断。

### 4.4 AuditPlanSnapshot

AuditPlanSnapshot 根据固定输入生成，并至少冻结：

- 本次适用的单域检查和跨域检查；
- 每项检查的槽位定义与关键性；
- 检查及槽位依赖图；
- 输入、事实、规范、企业制度和规则版本；
- 工具白名单、数据权限和用途约束；
- 数据时效、完整性和覆盖要求；
- 证据验证规则和最低结论策略；
- 执行轮次、成本、时间和重试边界；
- 补材料、人工复核和审批路由。

AuditPlanSnapshot 生成后，Agent 只能执行其中的任务，不能改写计划。

## 5. 法律域规则包设计

法律域不建议建设一个包含全部法律任务的“超级 Skill”。应当建设统一执行契约下的可组合规则包。

### 5.1 通用法律规则包

建议初步包含以下原子检查：

| 检查 ID | 内容 |
|---|---|
| `legal.party.identity` | 主体名称、身份和一致性 |
| `legal.party.authorization` | 签署人、代理关系和授权材料 |
| `legal.subject.scope` | 标的、范围、数量、规格和边界 |
| `legal.document.attachments` | 引用附件和外部文件的完整性 |
| `legal.price.definition` | 金额、计价方式、币种和税口径 |
| `legal.payment.conditions` | 付款节点、前置条件和义务触发 |
| `legal.performance.timeline` | 合同期限、履行里程碑和依赖条件 |
| `legal.delivery.acceptance` | 交付、验收、异议和不合格处理 |
| `legal.obligation.balance` | 核心权利义务的严重失衡 |
| `legal.breach.remedies` | 违约情形、补救、赔偿和违约金 |
| `legal.liability.cap` | 责任上限基数、范围及例外 |
| `legal.exemption.validity` | 免责条款与强制性限制 |
| `legal.termination` | 解除权、补救期、通知和终止后果 |
| `legal.term.renewal` | 合同期限、自动续约和退出窗口 |
| `legal.confidentiality` | 保密范围、例外、期限及返还销毁 |
| `legal.ip.ownership` | 既有成果、新增成果、许可和侵权责任 |
| `legal.dispute.resolution` | 法律适用、诉讼或仲裁安排 |
| `legal.effectiveness` | 生效日期、生效条件和签署要求 |
| `legal.notice` | 通知方式、地址变更和送达规则 |
| `legal.document.integrity` | 定义、编号、交叉引用、空白和冲突 |

规则应拆成可独立判定、独立引用证据、独立重审的原子检查，避免在一项规则中同时塞入违约、知识产权、保密、终止和争议解决等多个问题。

### 5.2 交易角色规则层

新系统不应只用“甲方/乙方”表示业务角色。应标准化为买方/卖方、客户/供应商、服务提供方/服务接受方、许可方/被许可方、披露方/接收方、出租方/承租方等语义角色。

交易角色用于：

- 确定规则适用性；
- 解释同一条款对我方的风险方向；
- 选择企业审查立场和可接受让步；
- 选择修订建议和审批路由。

### 5.3 合同类型专项规则包

建议逐步建设：

```text
legal.contract.core
legal.contract.purchase
legal.contract.sales
legal.contract.service
legal.contract.saas
legal.contract.nda
legal.contract.data-processing
legal.contract.amendment
```

执行时通过 AuditPlanSnapshot 组合，而不是让模型自由路由。例如，SaaS 采购可组合 `core + purchase + saas + data-processing`；保密协议可组合 `core + nda`并将明确不适用的价款或验收检查固定为不适用。

### 5.4 企业法律审查立场

企业审查指引不应是一段自由文本，应建模为版本化 LegalPosition，包含：

- 租户、适用组织和业务范围；
- 合同类型和交易角色；
- 主题与标准立场；
- 可接受的让步范围；
- 不可接受的条件；
- 金额、数据、业务或风险阈值；
- 例外和其有效期；
- 有权批准人或角色；
- 发布、生效、失效和审批记录。

平台法律规则与企业审查立场必须分开。企业立场可以更严格，或在法律允许范围内提供可批准让步，但不能覆盖平台的强制性法律规则。

## 6. 槽位模型

### 6.1 槽位的定义

槽位是完成一项检查必须获得的一个有类型、有证据要求、有依赖和有终态约束的业务单元。

槽位不是模型临时创建的问题列表。其定义来自已发布规则包，并在 AuditPlanSnapshot 中固定。

### 6.2 五类槽位

| 槽位类型 | 职责 | 示例 |
|---|---|---|
| 前提槽位 | 决定规则是否适用 | 合同类型、我方角色、法域、金额范围 |
| 事实槽位 | 描述已确认或候选事实 | 合同金额、付款比例、责任上限、未结余额 |
| 证据槽位 | 证明事实、规范或缺失 | 原文跨度、记录 ID、计算证明、规范引用 |
| 判断槽位 | 说明事实与规范之间的关系 | 法律效力疑点、制度偏离、数据覆盖充分性 |
| 行动槽位 | 描述后续处置 | 补材料、修改条款、人工复核、审批上报 |

### 6.3 槽位定义最小结构

每个 SlotDefinition 建议至少包含：

```text
slot_id
title
slot_type
value_schema
required / required_when
critical
dependencies
accepted_fact_types
evidence_policy
validation_rules
allowed_tools
allowed_terminal_states
invalidation_dependencies
```

其中：

- `required_when` 用于表达条件必填，例如只有存在责任上限时才必须计算上限基数；
- `evidence_policy` 说明是否必须有合同原文、规范引用、计算证明或缺失性证据；
- `allowed_terminal_states` 定义该槽位允许如何结束；
- `invalidation_dependencies` 定义哪些事实、材料、关系或规范变化时必须重审。

### 6.4 槽位业务状态

| 状态 | 含义 | 是否为终态 |
|---|---|---:|
| `pending` | 尚未处理 | 否 |
| `searching` | 正在搜索或调用工具 | 否 |
| `filled` | 已获得通过验证的值 | 是 |
| `not_found` | 在声明的覆盖范围内未找到 | 是，但必须有缺失性证据 |
| `not_applicable` | 确定不适用 | 是，但必须有适用性依据 |
| `needs_material` | 缺少明确材料 | 是，但会阻止关键检查自动通过 |
| `data_unavailable` | 数据源不支持、无权限、超时或错误 | 是，但会限制结论强度 |
| `conflicted` | 存在未解决事实冲突 | 是，通常转人工 |
| `undetermined` | 现有事实无法形成专业结论 | 是，通常转人工 |
| `human_review` | 已确定需人工判断 | 是 |
| `invalid` | 候选值未通过验证 | 否 |

“终态”表示自动执行对该槽位已有明确处置，不等于检查通过。

## 7. 示例：责任限制检查的槽位

`legal.liability.cap` 可包含：

```text
legal.liability.cap
├── applicability
├── clause_present
├── cap_basis
├── cap_amount_or_formula
├── covered_claims
├── carve_outs
├── indirect_damage_treatment
├── mandatory_law_conflict
├── enterprise_position_deviation
├── contract_evidence
├── normative_evidence
├── conclusion
└── recommended_action
```

槽位之间的关系例如：

- `clause_present = false` 时，`cap_basis` 与 `cap_amount_or_formula` 可不适用，但必须评估“无上限安排”对当前交易的影响；
- `cap_basis` 为费用期间公式时，必须识别期间、币种、已付/应付口径和关联订单；
- `mandatory_law_conflict = potential_conflict` 时，必须有版本化规范引用；
- `enterprise_position_deviation = beyond_fallback` 时，必须产生人工审批任务；
- `conclusion` 不得弱于前置槽位和固定风险策略形成的最低结论。

这个结构可防止 Agent 只找到“有责任上限”就宣告检查完成，而漏掉上限基数、责任范围、例外和法律效力。

## 8. 槽位验证门禁

槽位填充不能只做 JSON Schema 验证，应至少分为四层。

### 8.1 结构验证

- 必填槽位是否存在；
- 值类型、枚举、币种、单位和时区是否合法；
- 条件必填是否已触发；
- 依赖槽位是否已完成；
- 是否出现未在计划中的槽位或字段。

### 8.2 来源与版本验证

- 证据是否属于本次 InputSnapshot、FactSetSnapshot 和规范版本；
- 引文、表格单元格、JSON Pointer 或记录 ID 是否实际存在；
- 主体、合同版本、审批轮次和数据时点是否一致；
- 证据是否越过本次授权范围。

### 8.3 支持程度验证

- 证据是否能支持该槽位的具体值；
- 存在性证据是否被错用为完整性证据；
- 查询未命中是否有覆盖范围、分页完成情况和解析完整性证明；
- 计算是否保留输入、公式、口径、舍入及执行器版本；
- 规范依据是否适用于本次法域和相关时点。

### 8.4 语义与一致性验证

- 槽位之间是否自相矛盾；
- 结论是否弱于固定风险下限；
- 对数据缺口、事实冲突和工具失败的表达是否准确；
- 是否将模型建议伪装成合同原文或法律依据；
- 是否将未确认关系、参考级数据或上游意见当作确定事实。

高风险、关键阻断和“未发现”结论的支持程度验证应当更严。

## 9. 受控 ReAct 补槽循环

### 9.1 基本流程

```text
持久工作流读取 CheckDefinition 和 SlotState
                    ↓
根据依赖和权限选择本轮可处理的缺口
                    ↓
调度确定性执行器、检索、模型、Agent 或人工任务
                    ↓
获得 SlotCandidate / FactCandidate / EvidenceCandidate
                    ↓
进行 Schema、来源、证据、语义、口径和权限验证
                    ↓
接受有效候选，记录无效原因，更新 SlotState
                    ↓
重新计算关键槽位缺口
       ┌───────────────┼───────────────┐
       ↓                               ↓
当前快照内仍可自动推进         需要新材料、新授权或人工
       ↓                               ↓
进入下一轮定向补槽             持久暂停并创建 HumanTask
```

ReAct 是处理需要“观察—选择工具—继续观察”的任务机制，不是所有槽位的强制执行方式。

### 9.2 按槽位缺口定向执行

每轮不应重新执行整份检查。执行器或 Agent 的输入应包含：

- 固定规则和 Skill 版本；
- 当前允许读取的事实和材料；
- 已完成槽位及其受控引用；
- 未完成或未通过验证的槽位；
- 上一轮的具体验证失败原因；
- 本轮允许调用的工具和数据用途；
- 本轮的执行预算。

模型或 Agent 输出的是槽位增量补丁，不是对整个结果的任意重写。

### 9.3 执行方式选择

| 任务 | 优先执行方式 |
|---|---|
| 金额、比例、期限、阈值计算 | 确定性执行器 |
| 主体、账户、组织和关系匹配 | Adapter 或受控匹配工具 |
| 原文、条款、记录和规范定位 | 结构化检索工具 |
| 条款语义理解和候选判断 | 结构化模型调用 |
| 多步搜索和工具选择 | 受控 ReAct Agent |
| 规范依据 | 规则固定绑定 + 受控知识检索 |
| 事实冲突和超权例外 | 人工任务 |
| 修订建议和报告表达 | 模型候选草稿 + 结构化结论约束 |

不应为了“Agent 化”而将可确定计算的任务交给 Agent。

### 9.4 循环停止条件

“持续补槽直到完成”不等于无限循环。执行计划应固定：

- 单检查最大自动轮次；
- 单槽位最大尝试次数；
- 连续无新增有效槽位的停止阈值；
- 相同工具和参数的重复调用限制；
- 工具、时间、模型成本和 token 预算；
- 外部接口的重试与退避策略；
- 数据不存在、无权限、不支持、部分返回和超时的分类处置。

停止后，未完成槽位必须转化为明确的 `needs_material`、`data_unavailable`、`undetermined`、`human_review` 或执行失败，不得降级为“未发现风险”。

## 10. 完成门禁与固定聚合

### 10.1 槽位完成

槽位进入该 SlotDefinition 允许的终态，并满足相应的类型、证据、版本、权限和支持程度要求后，才视为完成。

### 10.2 检查完成

一项检查只有在以下条件同时满足时才能完成：

```text
所有必需槽位均进入允许终态
AND 槽位依赖满足
AND 证据门禁通过
AND 事实冲突已处理或明确转人工
AND 已形成结论及其最低处置要求
```

检查完成不等于检查通过。一项检查可以以“高风险失败”、“等待补材料”或“需人工复核”的完整状态结束。

### 10.3 AuditRun 完成

一次运行只有在以下条件满足时才可进入业务完成阶段：

- AuditPlanSnapshot 中所有适用关键检查都已完成；
- 所有适用关键跨域检查都已完成；
- 没有处于 `pending`、`searching` 或 `invalid` 的关键槽位；
- 所有补材料、数据不可用和人工复核事项都已形成明确任务或限制说明；
- 固定聚合策略已形成案件最低结论约束；
- 报告只组织已验证结果，不得改写其结构化含义。

### 10.4 最低结论策略

示例：

| 条件 | 案件最低结论约束 |
|---|---|
| 关键槽位缺材料 | 不得自动通过，等待补材料或人工承担限制 |
| 关键槽位事实冲突 | 不得自动通过，转人工确认 |
| 关键检查触发强制性法律风险 | 至少人工复核，视策略要求整改或阻断 |
| 企业立场偏离超出可接受让步 | 产生指定权限的审批任务 |
| 外部数据超时或覆盖不足 | 限制依赖该数据的结论，不得解释为无风险 |
| 非关键提示项未完成 | 按已发布策略决定是否降级，并在报告显示覆盖限制 |

不建议将正式结论简化为单一“合同安全分”。可以展示高/中/低风险数量、必审项完成率、证据覆盖率、规范引用覆盖率、未决事实数、补材料数和企业立场偏离数，但不以一个模型分数替代完成门禁。

## 11. 持久工作流与恢复

建议的检查执行状态：

```text
READY
  ↓
FILLING_SLOTS
  ↓
VALIDATING_SLOTS
  ├── 当前快照内可解决缺口 → FILLING_SLOTS
  ├── 缺用户或系统材料     → WAITING_MATERIAL
  ├── 等待外部数据           → WAITING_DATA
  ├── 存在冲突或需专业判断 → WAITING_HUMAN
  ├── 可重试执行失败           → RETRYABLE_FAILED
  ├── 不可恢复执行失败       → FAILED
  └── 所有必需槽位达到终态 → CHECK_COMPLETED
```

槽位状态和每次执行尝试必须持久化，以支持：

- Worker 崩溃或超时后从未完成槽位继续；
- 外部数据返回后定向恢复；
- 补材料或人工确认后重审受影响结果；
- 展示每个关键检查为什么完成、为什么暂停或为什么转人工；
- 防止已验证结果被新一轮模型输出无声覆盖。

补材料、新数据、人工纠正、合同版本变化或规范变化应形成新的输入修订或新运行。通过 ResultDependency 和槽位失效依赖图仅重算受影响部分；旧结果继续绑定旧快照。

## 12. 六领域的统一槽位执行模型

槽位模型不仅适用于法律域。

| 领域 | 典型槽位 |
|---|---|
| 法律审核 | 条款事实、规范依据、法律判断、修订建议 |
| 企业内部审核 | 制度适用、权限阈值、审批材料、例外授权 |
| 财务审核 | 主体映射、余额、到期口径、数据时点、覆盖和计算 |
| 合同关联 | 关系类型、双方版本、关系证据、置信度、验证状态 |
| 外部核查 | 主体匹配、查询覆盖、外部记录、时效、交易相关性 |
| 综合审计 | 前五域结果引用、跨域条件、事实冲突、最低结论和行动 |

跨域规则不应复制事实。它依赖已经验证的基础槽位和明确的数据覆盖。

例如“存量预付未结，新合同又要求高比例预付”可依赖：

```text
法律域：新合同预付比例、触发条件、退款与保障条款
财务域：存量预付余额、核销状态、截止时点和数据覆盖
合同关联域：存量往来与当前/历史合同的关联程度
综合审计：企业预付政策、反例与人工复核策略
```

任一基础槽位变化时，跨域结果通过依赖图失效并重算。

## 13. 建议的核心领域对象

本节只定义概念边界，不绑定存储实现。

```text
RulePackage
RuleDefinition
SkillBinding
SlotDefinition
AuditPlanSnapshot
CheckPlanSnapshot
SlotPlanSnapshot
CheckExecution
ExecutionAttempt
SlotCandidate
SlotState
ValidationResult
CheckResult
Evidence
Fact
FactConflict
ResultDependency
HumanTask
DecisionSnapshot
```

关键责任：

- RuleDefinition 定义要检查什么以及如何判定；
- SkillBinding 定义模型如何执行某个语义步骤；
- SlotDefinition 定义完成契约；
- AuditPlanSnapshot 固定本次检查范围和版本；
- CheckExecution 记录持久执行过程；
- SlotCandidate 是执行器提交的候选值；
- SlotState 是经验证的当前状态；
- CheckResult 是槽位收敛后的结构化结果；
- DecisionSnapshot 是有权人员对结果的决定记录。

## 14. 安全与权限边界

- 模型只能读取本轮槽位所需的事实和材料；
- 所有工具来自登记能力，按租户、法人/账套、案件、字段和用途授权；
- 外部数据只能经 Adapter 确定性解析后作为数据提供，其中内容不得作为系统指令；
- 敏感字段可在受控工具内比较，模型只获得匹配结果和必要引用；
- Agent 不得修改 AuditPlanSnapshot、FactSetSnapshot、规范原文、审批矩阵或已验证槽位；
- 模型修订建议只是候选草稿，需人工确认后才能由确定性修改器作用于固定文档版本；
- 日志记录业务事件、输入摘要、工具及模型版本、验证结果、成本和延迟，不保存模型隐藏思维链。

## 15. 评测与发布门禁

槽位驱动执行不能只评测最终文字答案。建议指标包括：

- 适用规则和必审项覆盖率；
- 关键槽位完成率；
- 槽位值正确率和类型合法率；
- 证据定位正确率和支持充分性；
- 缺失性证据可信度；
- 应为 `needs_material` 时的误通过率；
- 应为 `undetermined` 时的过度判断率；
- 事实冲突隐藏率；
- 规范引用的版本和适用性正确率；
- 关键风险漏报、误报和风险下限执行正确率；
- 重复执行的稳定性；
- 补槽循环的有效进展率；
- 无进展循环率和超预算率；
- 人工纠正后依赖失效与重审正确率。

金标应覆盖：

- 条款存在但对我方不利；
- 条款缺失；
- 引用附件未提供；
- 合同类型或交易角色不同；
- 规范依据不适用或已失效；
- 企业允许让步或存在有效例外；
- 主合同与补充协议冲突；
- 同一基础风险被多条规则命中；
- 工具超时、数据部分返回和权限不足；
- 事实冲突和人工确认；
- 有利条款被误报为风险；
- 修订建议与原结论不一致。

规则、Skill、验证器或执行器发布前，必须跑适用金标集，并保存版本、指标和审批记录。

## 16. 首期建设建议

首期不建议同时建设全部合同类型和六域规则。建议以一个试点场景验证完整机制。

### 16.1 定义试点边界

明确：

- 一个合同类型；
- 一个交易方向；
- 一个试点企业或法人范围；
- 一个主要使用角色；
- 明确的预审或正式节点用途；
- 一组真实脱敏样本。

### 16.2 建设第一个纵向切片

建议包含：

1. 10～20 个法律原子检查；
2. 少量企业制度和授权检查；
3. 每项检查的前提、事实、证据、判断和行动槽位；
4. 一个需要多轮补槽的复杂检查；
5. 一个缺附件后进入 `needs_material` 的场景；
6. 一个事实冲突后转人工的场景；
7. 一个跨域检查；
8. 补材料后定向重审；
9. 固定聚合策略和可追溯报告。

### 16.3 首期验收重点

首期应优先验证：

- Agent 无法跳过关键槽位；
- 存在结论但缺证据时不能完成关键槽位；
- 缺材料不会被误判为通过；
- 重复 ReAct 不会产生无限循环；
- 工作流中断后能恢复未完成槽位；
- 事实或材料变化后只失效相关结果；
- 跨域结果能引用而不是复制基础事实；
- 报告不会覆盖结构化结论或人工决定。

## 17. 待决策事项

1. 首个合同类型和交易方向。
2. 首期关键检查清单及关键槽位定义。
3. 哪些槽位状态允许检查结束，各自如何影响案件结论。
4. 哪些法律结论仅提示、哪些必须人工复核、哪些可要求整改或阻断。
5. 规则、Skill、规范知识和企业立场的审批及发布 DRI。
6. 每项检查的默认轮次、成本、时间和无进展停止阈值。
7. 规范引用的入库、更新、复核和历史回放要求。
8. 人工确认是仅对本案件有效，还是可以经审批沉淀为租户级事实或规则例外。

## 18. 最终设计结论

1. 法律域应建设可组合、可版本化的原子规则包，而不是一个包办所有任务的自由法律 Agent。
2. 结构化规则包是检查和槽位的唯一作者源，Skill 只是按需披露的受控执行说明。
3. AuditPlanSnapshot 必须在运行前固定适用检查、槽位、依赖、规范、企业立场、权限和执行预算。
4. Agent、模型、工具和执行器只提交候选槽位；应用层验证后才能进入 SlotState。
5. 持久工作流根据未完成槽位定向补槽，必要时暂停等待材料、数据或人工，不使用无限 ReAct 循环。
6. 关键槽位只有进入可验证业务终态后才算完成；缺材料、数据失败、事实冲突和人工复核都必须被明确表达。
7. 检查完成不等于检查通过；执行完成也不等于审批通过。
8. 六领域共用同一套槽位、证据、完成门禁、依赖失效和人工闭环机制，但保留各自的专业规则与权限边界。
