## 二、目标能力与优先顺序

方案要求法律知识域与企业知识域独立维护来源、版本、审批和权限，结论可区分依据；正式审查前固定授权材料与来源状态，先识别合同类型，再运行通用及有覆盖的专项审核；结果区分“合同审核发现 / 签约决策参考 / 审核范围与数据提示”。项目客户合同的 14 类上下游义务比对须有双边原文证据。真实财务与合同系统属于 MVP 后半段的验收内容，不可用模拟来源替代。以上目标在 [方案 §2～5、§8](../../整体方案设计指导与实现层级架构.md) 和 [实施计划 §2](实施计划与里程碑.md) 有明确依据。

执行顺序以 **M2 正式审查闭环 → M3 双合同闭环 → M4 真实只读来源 → M5 试点门禁** 为主线。M0 外部验证、领域金标及接口资料可以并行准备；它们各自的阶段门未通过时，相关功能保留开发态或受限状态。每次只选择一个能形成可演示纵向切片的 Goal，不以大量底层加固替代用户功能。

### 建议的第一个 Goal

“完成 P0，并交付 P1 中**一个明确规则**的可演示开发态纵向切片。”先读当前编译器的发布阻断与 Worker/结果路径，选最小规则，写出其输入、适用性、证据、无法判断和展示契约，再实现端到端。若领域语义尚未批准，交付候选和缺口清单即可；随后转到不依赖审批的权限/持久化/结果投影工程切片。不要以“完成 M2”作为单个 Goal 的初始目标。

## 四、Goal 模式执行约束

1. **一个 Goal 一个明确产物。** 进入前写清范围、前置条件、验收证据和最多 2～4 个有依赖顺序的子任务；每个子任务完成后更新本文件或相应 M 进展记录。不要同时推进 M2、M3、M4 的多个未闭环实现。完成一个阶段时及时commit&amp;push.
2. **先查已有实现再改。** 每轮核对最新提交、工作树、对应阶段记录和现有入口；只修与当前纵向切片有关的缺口。不要重复开发已完成的快照、候选契约或安全 helper，也不要覆盖他人未提交改动。
3. **阶段门与代码进度分开。** 将状态记录为“工程实现 / 已验证 / 领域批准 / 阶段门通过”四个层次。假模型、合成合同、fixture 和测试通过只计工程证据。G2 之前不开放正式审查；G3 之前不开放双合同运行；G4 之前不称真实系统接入已验收。
4. **跳过与延期有边界。** 当前 MVP 跳过补充协议待审、多层补充协议链、跨法人上下游关联、集团信用画像/复杂评分、全量法律采集、LLM-Wiki 自动发布、运行时任意外部 Tool/MCP、自建通用 ETL 和租户任意脚本。这些来自方案的当前范围/后续方向，不用它们作为当前 Goal 的前置条件。外部信息服务排在 MVP 末段；服务未定时先保留来源状态契约。不要静默跳过 14 类义务、权限、真实财务/合同接入和阶段门。
5. **外部依赖只等待一次，随后改做独立工作。** 缺法务裁决、企业知识审批、真实接口、模型凭证、真实样本或目标环境时，记录责任人、所需输入和受影响退出条件；在没有新证据前不反复询问、不循环改写同一文档/测试以制造进度。可转入同一里程碑的不依赖审批切片；若全部剩余任务都依赖同一外部输入，明确报告阻断并停止该 Goal，不伪造替代数据。
6. **重复失败设上限。** 同一根因连续两次修复/验证无新信息，先缩小复现并记录证据；第三次仍无进展则暂停该切片，列明根因假设、已试方法和下一项所需信息。网络/供应商/浏览器/本地 LibreOffice 环境问题区分代码缺陷；不无限重试命令或反复跑全量套件。Goal 的状态变更遵循运行环境规则，不能自行把未完成事项标为完成。
7. **验证与提交按风险。** 当前切片优先跑定向检查；涉及迁移、授权、任务/结果或跨进程边界，再跑相应集成与全量门禁。测试失败不得删掉断言来“通过”。每次收尾说明改动、证据、未验证项和对下个里程碑的影响；保存计划和进展记录，但不因文档更新自动变更阶段门。
8. **保护业务真相。** 法律原文与企业要求分源，未经批准的知识和候选输出不可升级为正式结论；缺数据、检索未命中、解析告警、类型不明分别显示为受限/待判定。冻结后材料或数据变化创建新快照/运行，历史结果保留；不得用前端遮挡代替服务端权限。
9. 遇到需要我确认的细节，按照你认为合理的推荐值执行，但是要详细记录在本文件里面。

## 七、下一阶段执行方案（2026-09-29）

### 7.1 总体策略

下一阶段继续以 M2/P1 为主线，先交付一个可演示、可追溯、明确受限的付款审查纵向切片；不在缺少领域输入时伪造 `legal.price.definition`、知识审批、金标或正式结论。M3 双合同 Worker、M4 真实来源接入和正式发布入口暂不提前启动。

执行顺序为：

1. 状态与文档收口；
2. 付款候选到受限 assessment 的服务端纵向闭环；
3. 外部规则/知识/QA 输入到位后的依赖规则执行与 completion proof；
4. 规则发布、撤回和 G2 质量门。

### 7.2 Goal 1：付款审查受限纵向闭环

**Goal 产物：**对同一冻结输入，完成“授权候选 → 服务端可信校验 → 规则 assessment → 持久结果 → 权限投影 → 三层展示”的开发态闭环。当前前置规则或语义未满足时，结果必须保持 `blocked`/`undetermined`，不得升级为正式审核结论。

**前置条件：**沿用现有 `contract_review` 单合同入口、InputSnapshot、FactSetSnapshot、规则定义快照和当前授权结果投影；不引入未经批准的业务语义。

**子任务：**

1. **状态收口。**确认工作区 `docs/arch` 删除项是否为用户既定变更；修正本计划中已过期的工作区描述；同步 M2 进展记录中的最新验证口径。
2. **可信槽位提交适配器。**仅接受当前冻结输入、当前授权来源、已校验证据和已确认事实；拒绝跨运行、跨 FactSet、失效授权、缺少直接证据或未实现槽位。对 judgment、付款比例、数组量化等未批准/未实现语义继续 fail closed。
3. **assessment 与结果闭环。**执行并持久化 `RuleRun.assess()`，保存提交槽位、证据身份、缺失材料、未完成依赖和限制原因；结果 API 与本地摘要继续显示规则、来源、FactSet、TaskResult 和 assessment 身份。
4. **结果展示与回归。**三层结果页明确区分“合同审核发现”“签约决策参考”“审核范围与数据提示”，候选、待确认、阻断原因和证据回跳保持可见；补齐撤权、错绑输入、FactSet 变化、证据缺失和失败重试测试。

**验收证据：**

- 同一冻结输入可复现同一 assessment 身份和限制原因；
- 任一授权、证据、输入快照或事实快照不匹配都不能生成确定结论；
- `legal.price.definition` 缺失时仍明确返回 blocker，不能以依赖图、哈希或人工事实确认替代；
- 完成定向规则/Worker/API/UI 测试，并按迁移、授权、任务和结果风险运行相应数据库纵向回归；
- 更新 M2 进展记录和本计划，说明工程实现、验证范围、领域批准和阶段门状态。

**建议提交拆分：**状态与文档收口；服务端可信槽位与 assessment 链路；结果展示、回归测试和进展记录。

### 7.3 Goal 2：依赖规则执行与 completion proof

**启动条件：**收到并核验 `legal.price.definition` 规则源、付款语义、法律依据/企业立场版本，以及可用于验收的独立金标和阈值。在这些输入到位前，只保留工程接口和显式 blocker。

**交付内容：**

- 增加真实依赖 RuleDefinition 及规则级样例；
- 按冻结拓扑执行依赖规则，并绑定同一 case、InputSnapshot、FactSetSnapshot；
- 仅从已授权且哈希复核的持久结果生成 completion proof；
- proof 绑定规则版本、知识版本、TaskResult、assessment、definition manifest 和证据摘要；
- 输入、事实、材料、规则或知识版本变化时强制重新执行；
- 依赖结果仍按当前调用者权限投影，不因内部存在结果而扩大可见范围。

**验收证据：**依赖规则成功/失败/待判定/缺材料均有明确状态；旧 FactSet、旧规则版本、失效授权和篡改结果均不能生成或复用 proof；`completed_checks` 只能由可验证 proof 派生。

### 7.4 Goal 3：G2 规则发布与质量门

**启动条件：**Goal 2 的规则执行链路可验证，且法务、企业知识负责人、QA 和 Approver 提供正式输入。

**交付内容：**

- 建立规则、Skill、法律知识、企业知识和评测报告的候选→复核→批准→发布→暂停/撤回生命周期；
- 发布记录绑定版本、源文件哈希、知识身份、评测报告、批准人、批准时间和回滚目标；
- Approver 与 Author 分离，正式入口默认关闭直到发布门通过；
- 独立金标覆盖正例、反例、缺材料、冲突、边界和安全类别，并记录批准阈值；
- 规则版本只影响新运行，历史运行继续使用其不可变快照。

**G2 退出条件：**发布审计不再固定为开发态 blocked；未批准材料不能形成正式结论；内容、阈值、权限、回滚和审计记录均可核验。未满足任一项时，系统继续停留在开发态/受限态。

2. 对含税价、未税价、税额、固定金额和比例执行精确十进制核算。
3. 对正文、价款表、附件、补充协议保留全部证据并生成冲突提示。
4. 将价款槽位状态、核算提示和证据写入现有 TaskResult。
5. API 返回价款槽位和人工核对原因；本地 Markdown 摘要同步展示。

**完成凭据：**

- 正常合同、税额冲突、金额冲突、分母缺失四类端到端案例均可回放。
- 价款候选和付款候选均绑定同一 InputSnapshot、文档版本和原文证据。
- 缺失/冲突只影响相关判断，不阻断违约责任、交付周期等其他检查。
- 不产生无证据的“通过”或“不通过”。

### Goal 5：接通跨规则结果传递

**目标：**`legal.price.definition` 的开发态结果可以作为 `legal.payment_conditions` 的前置结果使用，但不能用字符串或哈希伪造完成状态。

**执行任务：**

1. 从持久 TaskResult 选择同一合同、同一 InputSnapshot 和同一事实快照的价款结果。
2. 校验规则版本、规则源哈希、结果哈希、证据哈希和执行状态。
3. 生成带来源绑定的依赖结果引用。
4. 仅在开发阶段允许的状态策略下传递给付款规则；缺失或冲突继续保持 `blocked/undetermined`。
5. 增加重复结果、旧事实快照、跨合同和篡改哈希的 fail-closed 测试。

**完成凭据：**

- 价款规则先执行，付款规则后执行，顺序由依赖图决定。
- 任一输入、规则源或结果哈希不匹配时，付款规则不执行后续确定性判断。
- 依赖结果引用可从 API 和运行摘要追溯到原始结果。

### Goal 6：完成产品界面和人工复核闭环

**目标：**审核人员能直接看懂价款判断、原文证据、冲突原因和下一步人工动作。

**执行任务：**

1. 结果页增加“合同价款口径”区块。
2. 分开展示含税价、未税价、税额、币种、付款分母和阶段金额。
3. 同一判断涉及多个原文位置时全部展示。
4. 对缺金额、税额冲突、来源冲突、比例分母不明显示人工任务。
5. 支持从人工复核任务返回补充材料或确认记录，并保留审计轨迹。

**完成凭据：**

- 页面、API、本地摘要三处字段名称和状态一致。
- 用户不需要阅读 JSON 即可理解每个价款结论。
- 高风险案例只显示“待人工决策”，不自动替人批准。

### Goal 7：开发态验收与发布准备

**目标：**完成一套可重复的开发态回归，同时明确哪些内容仍属于后续生产升级。

**执行任务：**

2. 每次运行生成 observations、中文可读报告和哈希。
3. 记录开发态通过率，但暂不把它解释为正式漏报率/误报率。
4. 对规则源、评测套件、观察结果和报告执行一致性校验。
5. 形成生产升级清单：法律正文、企业制度、审批、正式阈值和真实金标。当前清单见 [规则生产升级前置清单](../06-rules/生产升级前置清单.md)，各项未提供真实责任人证据前均不视为完成。

