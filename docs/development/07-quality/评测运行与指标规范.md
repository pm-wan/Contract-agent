# 规则评测运行与指标

> 版本：v0.1｜状态：开发评测技术规范；尚非验收阈值或发布批准
> 适用：M2 开发集/回归集评分基础
> 上游：[金标建设规范](金标建设规范.md)、[规则发布流程](../06-rules/规则发布流程.md)

## 1. 范围与边界

评测器只比较已产生的结构化观察结果与评测套件中的显式期望；不调用模型、不生成或修改标签、不裁决法律含义，也不替代人工复核。当前 `legal.payment_conditions.cases.yaml` 是 `approved_for_development` 的合成开发种子，不是独立验收集或已批准金标。

没有 QA 与领域负责人批准的阈值时，评测器必须报告 `blocked_no_approved_thresholds`，即使所有样例字段均匹配也不得返回发布通过。该规则有意阻止将“测试样例跑通”误报成 M2 发布验收。

## 2. 观察结果输入

每行一个 JSON object，至少有 `case_id`，其余字段按 suite 的 `expected` 结构提供。字段值必须来自对应执行记录；评测器不会把缺失字段推断为正确。`slot_values` 按槽位 ID 提交 `{state, value, evidence_spans}`；评分时用本次精确编译的 Rule Schema 校验槽位存在性、允许状态及 `filled` 值类型，并验证候选引文与固定 fixture 完全一致，且必须包含在该观察的 `evidence` 中。未填充状态必须为 `value: null`。这样既比较阶段/触发事实本身，也阻断字段拼写、类型漂移和候选值脱离证据。`direct_evidence_required` 比较观察字段 `direct_evidence`；`minimum_severity` 使用低 < 中 < 高 < 严重的序关系；`forbidden_judgments` 中任何命中都使样例失败；嵌套对象按期望字段递归比较。

同一 suite 内缺少观察记为失败；未知或重复 `case_id` 视为输入错误并拒绝评分。观察记录按 `case_id` 规范排序后计算 SHA-256，因此记录行顺序不影响评测输入指纹。

## 3. 当前报告指标

- 新报告使用 `report_version: "1.2"`；逐例记录写入 suite 声明的 `kind` 和 `observed`，以区分缺失观察与已观察但不匹配的结果。校验器兼容 `1.0` 与 `1.1` 报告。
- `case_count`：suite 样例数；缺失观察仍计入分母。
- `observation_count`：实际提供的观察数。
- `passed_case_count` / `failed_case_count`：满足全部显式期望的样例数 / 未满足数。
- `case_pass_rate`：`passed_case_count / case_count`，仅为描述性指标，不是发布阈值。
- `by_case_kind`：按 suite 原有 `kind` 分组，逐组报告相同的样例数、观察数、通过/失败数和描述性通过率；只列该 suite 实际出现的分类，报告校验器从逐例记录重算并核对。它不增加类别、金标、权重、阈值或发布结论。
- `missing_case_kinds`（v1.2）：列出固定允许类别（`positive`、`negative`、`missing_material`、`conflict`、`boundary`、`security`）中 suite 完全没有的类别；由校验器从逐例行重算。它只暴露数据覆盖空白，不把缺失类别改成失败样例，也不设覆盖门槛或发布结论。
- `suite.source_sha256`、`suite.fixture_manifest_sha256`、`suite.rule_sha256`、`observations_sha256`：标识评测套件、固定材料夹具、精确规则源和观察输入；命令会验证 suite 的 `rule_ref` 与实际编译规则 ID/版本一致，并在报告逐样例列出失败条件。
- `report_sha256`：对移除此字段后的完整规范化 JSON 报告计算 SHA-256；可检测意外损坏，但不是签名，无法证明报告由特定 QA 或领域负责人生成。

## 4. 运行方式

```bash
uv run python scripts/evaluate_rules.py \
  --suite docs/development/06-rules/eval/legal.payment_conditions.cases.yaml \
  --rule docs/development/06-rules/rules/legal.payment_conditions.v1.yaml \
  --observations /secure/evaluation/payment-observations.jsonl \
  --report /secure/evaluation/payment-report.json \
  --markdown-report /secure/evaluation/payment-report.md

uv run python scripts/verify_evaluation_report.py \
  /secure/evaluation/payment-report.json
```

`--report` 以 `0600` 权限创建新 JSON 文件，拒绝覆盖已有目标；`--markdown-report` 可同时生成同样以 `0600` 创建的中文摘要。Markdown 由已验证评分对象确定性渲染，不重新评分、不生成 observations。省略报告选项时只输出至 stdout。格式错误以退出码 1 结束；有效评分因尚无批准阈值仍以退出码 2 结束，即使报告成功保存亦然。校验命令验证 JSON 报告封闭结构、总体及分类指标与逐例记录的一致性、自哈希和 JSON 键唯一性，完整性正确时退出码为 0；这不代表评测通过或达到发布资格。观察文件和报告应作为受控评测产物管理，不提交合同原文、个人信息或未授权材料到仓库。

## 5. 升级为发布门之前

发布门仍需 QA 与领域负责人共同批准并版本化：独立验收集、样例材料/引用定位、规则版本绑定、严重漏报与错误通过口径、分层阈值、红队样例和审批身份。达到这些前置条件后，才能设计并实现阈值文件及 gate 状态；不可在本技术规范中代填业务阈值。
