# PRD：首期合同审计

> 版本：v2.0 候选｜状态：待评审
> 上游：[9 月 24 日方案](../../整体方案设计指导与实现层级架构.md)、[首期范围](../00-project/首期范围说明书.md)

## 1. 用户目标

工作人员在签署前审查我方作为采购方的服务及软件采购主合同，既能检查合同条款，也能按需参考已签历史合同、财务往来和项目客户合同。每项结论应知道依据、来源时间、覆盖范围和是否需要人工确认。

## 2. 用户流程

1. 创建案件时主体暂空，先上传待审主合同；在工作人员确认签约主体前，不允许上传附件、选择材料、授权模型读取或冻结审查输入。
2. 审核人依据签约资料确认并记录主体及核对依据；确认主体不是由模型推断，也不自动合并集团内不同法人。主体确认后锁定，普通审核人不得直接修改；如需纠错，只能由当前租户的主体管理员按纠错流程操作并留下不可变审计。管理员通过受信运维流程预置/撤销，与 `operator` 运维身份分离。主体管理员即使不是案件成员，也可通过独立纠错队列处理本租户案件；队列只显示案件名称/ID、当前主体 UUID 和版本，独立纠错上下文只返回案件 ID、当前主体 UUID 和版本，不返回合同材料、运行结果或普通案件详情，也不自动授予案件成员身份。管理员可在材料选择、授权或输入冻结之后纠错：纠错会撤销现有材料选择及其模型读取授权、递增案件版本，并将绑定旧主体范围的运行标记为已替代；旧冻结快照与运行记录保留为历史，不原地改写。已上传 `DocumentVersion` 保持不可变且仍绑定原主体，新主体下重新审查须由案件成员上传对应新材料版本、重新选择并授权，再预览/冻结；旧结果的读取仍服从当前成员及材料授权检查。确认后才开放附件上传及按法人范围的逐份授权。
3. 查询该签约主体的曾签历史合同候选；工作人员选择背景合同。候选列表和摘要不得展示金额或可反推出金额的信息。
4. 若需上下游分析，工作人员选择或上传同一我方法人项目的客户合同；无需手工标记条款。未选择时常规审查仍可继续。
5. 查询已启用且获授权的财务及其他来源；展示来源、时间、完整性和失败状态，供工作人员预览确认。
6. 冻结本次材料、关系、查询结果和知识版本；识别合同类型，运行通用检查及有覆盖的专项检查，并自动比对 14 类上下游义务。
7. 分别查看合同审核发现、签约决策参考、审核范围与数据提示；处理人工复核、补材料和重审。材料或查询结果变化产生新运行。

## 3. 核心行为

- 上下游每项判断有上游要求、下游对应条款、双方原文定位、适用性、覆盖状态和解释；状态为已覆盖、部分覆盖、未覆盖、存在不一致、不适用。材料未取得或不可读时不冒充“未覆盖”。
- 类型不确定时仍执行通用检查；混合内容只运行有对应覆盖的专项检查，并说明未覆盖部分。
- 财务/经营/信用信息用于签约决策参考，不自动构成合同条款缺陷；法律依据与企业内部要求分别标注。
- 未启用、无权限、无记录、部分返回、失败和过期各有不同状态；依赖该来源的检查不得因数据缺失显示为通过。
- 服务端在模型读取、摘要、结果、报告和导出环节执行当前权限。选择另一份合同不自动授予全文或金额读取权。
- 系统仅提供辅助建议，不自动批准、签署、盖章或回写正式审批流程。

## 4. 分阶段交付

前半段用模拟来源跑通主体确认、选择、预览、冻结、审查和三类结果；当前开发版只提供已有运行结果查看，不开放真实合同启动。后半段开始时再按真实财务/合同 API 完成详细设计、联调与验收，外部经营/信用信息在末段接入；MVP 前半段不要求预先完成真实来源查询的冻结协议设计。模拟来源不计作真实接入完成。全部 14 类属于最终 MVP 验收范围，可分批开发。

## 5. 未决实施事实

财务字段与业务口径、合同系统候选和授权接口、外部服务与数据授权、实际样本负载和新成本目标由[实施计划](../00-project/实施计划与里程碑.md)对应阶段确认。补充协议待审、跨我方不同法人的项目义务映射和运行时 Skill 自行调用 Tool 不在本轮。
