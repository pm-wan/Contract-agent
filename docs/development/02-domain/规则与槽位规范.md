# 规则与槽位规范

> 版本：v1.1 候选｜状态：按新范围修订中
> 负责人：内部规则负责人
> 批准人：内部项目发起人
> 适用阶段：M0～M4
> 上游依据：领域模型 v1.0、规则 Schema v1.0  
> 详细 Schema：`../06-rules/规则Schema.md`

## 1. RuleDefinition 责任

定义“何时检查、检查什么、需要什么证据、如何形成最低结论以及何时转人工”。规则不能只是一段 Prompt。

## 2. 槽位分类

| 类型 | 示例 |
|---|---|
| prerequisite | 合同类型、角色、法域 |
| fact | 付款比例、责任上限、余额 |
| evidence | 原文、计算、规范引用 |
| judgment | 企业立场偏离、法律疑点 |
| action | 补材料、修订、上报 |

## 3. 槽位终态

`filled`、`not_found`、`not_applicable`、`needs_material`、`data_unavailable`、`conflicted`、`undetermined`、`human_review`。

终态表示自动处理已有明确处置，不表示通过。

## 4. 完成条件

```text
必需槽位进入允许终态
AND 依赖满足
AND 证据门禁通过
AND 冲突已处理或转人工
AND 结论不弱于固定风险下限
```

## 5. SkillBinding

SkillBinding 只能定义某一语义步骤的执行说明、输入输出 Schema、工具边界和预算。它不能修改 AuditPlanSnapshot、选择冲突真值或批准例外。

平台正式运行使用 MD Skill 文本，绑定已发布规则、知识版本、内容哈希和许可的任务/工具；版本与审批元数据将来可以由数据库管理。仓库 `skills/` 下的开发用 MD 不能因被模型读取就成为正式规则。规则和结果需明确 `knowledge_domain`、`basis_kind`、依据版本、适用时点与责任人；法律要求、企业要求及交易背景分别形成判断或以有来源的聚合项关联。

上下游义务比对以 14 类为目标，逐项输出适用性、上游原文、采购条款、五种覆盖判断及缺材料/不可读限制。后台检查状态与面向用户的三类信息结果分开。

## 6. 重审

每个槽位声明 invalidation_dependencies。合同、事实、关系、规范、规则或权限变化后，应用沿依赖图标记结果 stale 并创建新运行。

## 7. 状态映射

槽位状态不得直接冒充检查判断。最小映射规则：

| 条件 | 检查判断下限 |
|---|---|
| 关键槽位 needs_material | needs_material |
| 关键槽位 conflicted | human_review |
| 关键数据 data_unavailable | undetermined 或 human_review |
| 关键槽位缺少有效 direct evidence | human_review |
| 适用性确定为否 | not_applicable |
| 执行器失败 | 不产生判断；运行进入失败/重试状态 |

只有规则明确声明且证据门禁通过时才能形成 `passed`。
