# 事实与证据模型

> 版本：v1.1 候选｜状态：按新范围修订中
> 负责人：内部规则负责人 + 技术负责人
> 批准人：内部项目发起人
> 适用阶段：M0～M4
> 上游依据：领域模型 v1.0、用户故事与验收标准 v1.0

## 1. Fact 最小结构

```text
fact_id
tenant_id / case_id / snapshot_id
subject_ref
predicate
typed_value
unit / currency / tax_basis
scope
valid_time / as_of / observed_at
source_refs[]
mapping_or_extractor_version
verification_status
confidence（仅候选使用）
version
```

合同金额、流程表单金额、财务余额、实收实付和未入账承诺是不同 predicate，不得互相覆盖。

## 2. 来源权威策略

| 事实 | 首选来源 | 限制 |
|---|---|---|
| 合同约定 | 固定合同原文 | 只证明文字约定 |
| 财务余额 | 指定账套快照 | 只证明账内记录 |
| 流程状态 | 指定流程实例 | 只证明系统状态 |
| 主体身份 | 主数据 + 授权确认 | 名称相似不是同一主体 |
| 合同关系 | 源系统显式关系/人工确认 | 模型推断只能作候选 |

## 3. Evidence 类型

- document_span：页、段、条款、字符或单元格；
- source_record：数据源、记录 ID、JSON Pointer；
- calculation：输入、公式、口径、舍入和执行器版本；
- normative_reference：规范 ID、版本、条款和适用时点；
- human_confirmation：确认人、权限、理由和时间；
- absence_evidence：材料范围、解析覆盖、搜索方法和未命中说明。

项目上下游比对的证据应分别保存客户合同与采购合同的固定版本、条款坐标和原文哈希；没有对应条款须有下游检索范围及解析覆盖，不得把“上游合同未提供”或“文档不可读”记为下游未覆盖。每条未命中检索轨迹应绑定具体义务类别和采购合同版本，不得将一个类别的检索范围复用于另一个类别。财务和外部来源证据另记查询范围、授权、来源状态、`as_of`、`fetched_at`、分页完整性和原始记录引用。

## 4. 证据门禁

按结构、来源与版本、支持程度、语义一致性四层验证。高风险和“未发现”结论执行更严格验证。

## 5. FactConflict

冲突记录保留全部候选、差异类型、受影响检查、处置状态和决定。允许的处置包括：选择、并存、要求新材料、限定适用范围和转人工。

## 6. 定位坐标

首期固定 Unicode/字符偏移口径，同时保存页码、条款路径和文本哈希。前端不得直接混用后端 Python 字符索引与浏览器 UTF-16 offset；API 明确 offset 单位并提供统一转换/引用定位逻辑。

MVP 的 `start_offset`、`end_offset` 统一定义为解析后规范化文本的 Unicode code point 半开区间 `[start, end)`；API 同时返回 `quote` 与 `text_hash`，前端以 quote/hash 校验后高亮。PDF bbox 使用页面坐标，原点和单位由 parser 输出声明。

## 7. 验证状态

Fact 的 `verification_status` 固定为：`candidate`、`verified`、`rejected`、`conflicted`、`superseded`。模型只可创建 candidate；verified 必须来自确定性映射或有权人工确认。

Evidence 的支持关系固定为：`direct`、`corroborating`、`context`、`contradicting`。关键判断至少需要一条 `direct` Evidence；absence_evidence 还必须包含搜索范围、解析覆盖率和查询方法。
