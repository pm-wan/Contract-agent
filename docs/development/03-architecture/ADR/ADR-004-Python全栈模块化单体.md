# ADR-004：MVP 采用 Python 全栈模块化单体

> 状态：候选（本实施计划的基准决策；M0 Spike 后转为已接受或重新评审）｜日期：2026-09-25
> 取代：ADR-001 的 Go 主栈结论和 ADR-003 的语言/框架组合；不取代 ADR-002 的应用拥有持久工作流原则。

## 背景

9 月 24 日方案把文档解析、原文定位、授权上下文、计划执行和证据回跳放在核心链路上。团队明确倾向 Python 全栈。Python 文档处理生态成熟，PageIndex 当前提供 Python SDK 与本地索引模式，AgentScope 也提供 Python agent 执行能力。MVP 尚无需 Go 的性能、团队标准或部署限制证据；Go + Python sidecar + TypeScript 会提前形成两套后端运行时。

同时，合同审核对权限、审计和确定性工作流要求高，不能因采用 Python 或 AgentScope 而把业务真源交给 Agent/SDK。

## 决定

1. MVP 后端、Worker、领域应用和文档/检索 adapter 统一采用 Python。前端框架与 UI 已定为 React + Ant Design；本 ADR 不锁定前端语言、版本及路由/状态/构建配套工具。
2. 工程形态为模块化单体：单仓、清晰 package 边界，API 与 Worker 可作为独立进程部署；初期不拆微服务。
3. AgentScope 是受限的局部 Agent 执行器；PageIndex 是可替换的检索 adapter。二者不得进入领域模型或承担权限、任务状态和业务结果真源。
4. PostgreSQL 保存案件、授权、运行计划、任务租约、输入冻结引用、结果、人工决定和审计；对象存储保存原件及不可变产物。应用自有工作流保证幂等、重试、取消、恢复和审计。
5. PageIndex MVP 优先验证本地模式；Cloud/MCP/外部 OCR 不默认启用，须先通过数据托管、授权、区域、保留及安全评审。
6. 9 月 17 日针对 10 周旧范围的工期、成本和验收结论不作为新计划承诺；按新阶段门重新估算。

## 备选方案

| 方案 | 评估 |
|---|---|
| Go + Eino 主后端 + Python 解析侧车 | 可靠且可行，但 PageIndex/AgentScope/文档工具仍要经跨语言边界；目前缺少足以抵消双运行时成本的容量或运维证据 |
| Python + AgentScope | 当前优选；工具链相邻、易于纵向验证；需通过持久任务、类型/依赖边界、性能和恢复测试避免脚本式单体 |
| Python 主业务 + Go 推理/工作流服务 | 不采用；在业务边界未稳定前会分裂数据所有权、故障定位和部署职责 |

## 后果

- 正面：解析、PageIndex、本地数据与 Agent 适配可在一个语言栈完成；减少跨服务 DTO、网络故障和双后端构建维护。
- 代价：需自律建立 Python 模块边界、类型检查、依赖锁定、SQL/事务规范与压力验证；CPU 密集解析通过 Worker 并发和进程隔离控制。
- PageIndex 的本地模式对扫描件/图像型 PDF 能力有限，须有 OCR/预处理适配器和质量降级策略；托管 Cloud 不是默认补救方案。
- Python 全栈不等于全部单进程。API、Worker、OCR 可按资源隔离运行，但保持一个应用代码库和明确数据所有权。

## 验证与接受条件

M0 必须完成技术栈基线 §9 的六项 Spike，尤其是：PageIndex 对合同样本的引用定位和权限隔离、扫描件路线、AgentScope 的取消/恢复、PostgreSQL job fencing/幂等、API/Worker 重启恢复、固定金标上的质量/费用/延迟。接受决策须附运行记录、测试报告、版本与许可证清单。

## 回滚/重评条件

遇到以下证据之一时新建 ADR 评估局部 Go 服务或其他技术，不直接推翻所有 Python 模块：明确的客户私有化/运行环境约束；Python 对目标吞吐或资源预算连续无法达标且优化无效；组织平台标准要求；PageIndex 部署模式不能通过权限/数据评审；AgentScope 或核心 Python 依赖无法满足许可证、安全、恢复要求。优先保持 API/Worker 的语言中立契约和业务 DTO。
