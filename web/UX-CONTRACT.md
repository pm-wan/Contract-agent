# Web UX Contract

> Applies to the React + Ant Design internal contract-review workbench. Reviewed 2026-10-12. This file records observable UI behavior; business policy remains in the linked sources.

## Product context

- Audience: Chinese enterprise contract reviewers and business staff preparing procurement contract reviews.
- Primary job: choose between a quick single-contract review and a prepared review, then upload the main contract, explicitly start review, and read results with source evidence. Background information and related contracts support the prepared path.
- Market and active locale: China; `zh-CN` Simplified Chinese.
- Language/content register: concise operational Chinese; do not call unverified information a review conclusion.
- Timezone: show API timestamps in `Asia/Shanghai`; retain the source timestamp and offset when available.
- Accessibility target: WCAG 2.2 AA.

## Current workflow decision (2026-10-12)

The home page presents two entry paths: `快速审核` creates a case from one uploaded main contract and proceeds without requiring related contracts or background materials; `准备完整审核` creates a case first so the reviewer can assemble background information and related documents. The cases page remains the place to find existing work. Quick intake pre-fills an editable case title from the file name. An uncertain upload keeps the created case, exact file and upload key for retry rather than creating another case.

The case detail has three URL-backed sections: `背景与材料` (`view=background`), `审核过程` (`view=review`), and `审核结果` (`view=results`). Existing-case links default to background; quick intake explicitly opens review, prepared intake opens background. Background shows subject preparation and a material catalog with file type and parse/index state. Process shows the main-contract start action, authorization controls and execution history. Results shows only completed/waiting batches as produced-result entries; queued/running batches stay in execution history and indicate pending results. Navigation preserves form values within the current case and restores its location on Back/reload. Necessary subject confirmation and explicit text/amount authorization are collected in one `开始审核` modal. The user selects a grant duration; no amount consent is inferred. Existing valid full grants are reused. An existing text-only grant is not broadened: the UI directs the reviewer to explicitly revoke/re-authorize through the review-scope disclosure. After confirmation the frontend sequentially checks current case/material state, confirms the subject if needed, selects/authorizes the main file, previews the server scope, freezes it, and creates a run. Every selected contract-review attachment is included and disclosed. Multiple unselected main contracts require an explicit choice; an existing selected main stays authoritative.

Subject preparation belongs to background. Review-scope permissions, manual input preview/freeze, and subject/material audit records each have a separate disclosure within process. Case identifiers and concurrency versions are secondary archive information. No editable project-background fields are exposed because the API cannot persist them. Development/test execution requires `CONTRACT_REVIEW_EXECUTION_ENABLED=true`; production remains unavailable. This replaces older Web-start-closed statements for this local development slice only. The processor currently produces payment/price candidates; the planned legal and company-standard review and fuller prepared-review behavior are not implemented yet and must not be presented as available results.

Pending parse/index states refresh serially every 2.5 seconds while the case is open; read failure stops the loop and requests explicit refresh. Every successful upload/authorization update refreshes case and documents together. Starting a run uses one retained request key; an uncertain freeze reuses the same preview and an uncertain run start reuses the same frozen input/key. A deterministic version conflict requires a fresh check. No workflow state is persisted in browser storage. A page reload recovers committed runs through case execution history. Queued/running history refreshes every three seconds while the process/results section is active; a failed request pauses automatic refresh until the user retries.

## Visual contract

- Project `DESIGN.md`: repository root; preserve its case-file/index-margin direction and existing tokens.
- Token ownership: `web/src/design/tokens.ts` is runtime source; it maps to Ant Design `ConfigProvider` and CSS custom properties. `DESIGN.md` mirrors accepted values.
- Supported theme: light only. No token changes are introduced by this workflow.
- Shared visual shell: existing Ant Design `Layout`, `Menu`, `Breadcrumb`, `Table`, `Alert`, `Spin`, and `Upload`/native picker patterns, styled through project CSS and tokens.
- Run detail (`/runs/{runId}`) uses an archival reading layout: one case-file header, a compact scope boundary, candidate results in the primary column, and a page-index rail for result and citation navigation. Run/input identifiers stay inside a disclosure. Citation markers use the documented bronze token and link to the existing verified-source drawer; no dashboard metric cards or duplicate finding summaries are added.
- The upload-role and authorization-duration fields intentionally use native `<select>` controls; the browser/OS owns their opened popup geometry and platform interaction. We accept that ownership because these are short, low-frequency enumerations rather than authored menus; do not style the native popup or replace it without a project-wide accessible Select owner and browser verification.

## Dataset navigation

- Case list is a searchable server-paginated table (`page`, `page_size`, title-only `query`); defaults are page 1 / 20 rows; page size choices are 10, 20, 50, and 100.
- The URL owns committed query, page, and page size. Search input updates immediately, commits after 300 ms, is IME-safe, and has an explicit clear control. Changing query or page size resets page to 1.
- API reports `items`, `total`, `page`, and `page_size`; the UI displays total count and clamps to the server-returned page.
- Initial load reserves a stable table area and uses an Ant Design spinner. Refresh keeps the current table visible until the new page arrives. Empty dataset, no search results, 401, 403, 404, and service failure use distinct copy and recovery.
- Rows navigate through a real link to `/cases/{caseId}`. Browser Back returns to the prior list URL and state.

## Navigation and responsive behavior

- Route titles: `首页 — 合同审查工作台`; `案件列表 — 合同审查工作台`; `案件详情 — 合同审查工作台`; include non-sensitive case title only when useful.
- Lazy-loaded case-detail, run-result, and human-task routes retain the shared shell, announce a reserved-region loading status, and set a truthful loading document title until the page sets its own title. Lazy-loaded run-history and authorization-history panels show local status without blocking the case detail route. If any lazy module fails to load, an app-owned recovery page keeps the shell and offers an explicit page reload; raw exception data is not rendered.
- 401: identity is not configured/has expired; show local development setup guidance only in the local development surface, otherwise direct the user to the organization’s authentication administrator. Never retry in a loop.
- 403: explain access is denied without exposing case/document metadata; offer return to the case list.
- 404: explain the case is unavailable or does not exist; do not call it an authorization failure.
- 5xx/network: retain list/search URL and upload queue; offer explicit retry; never display raw server details.
- At 720px and below, the case and human-task tables retain horizontal scroll and visible overflow; essential names/status/actions remain available. Detail/document content reflows to one column and document names wrap. The collapsed-sidebar trigger stays within the top-bar reservation and must not overlap page headings or controls.
- Breadcrumbs represent hierarchy and mark current page. Focus moves to the route heading after client-side navigation.

## Overlays and feedback

- Use Ant Design modal/form primitives for app-owned overlays; no browser-native alert/confirm/prompt.
- Routine list refresh is inline. Upload uses a per-file live status instead of a toast so a multi-file batch cannot flood notifications. Action and acknowledgement labels must match.
- Upload success is not an authorization grant. Display `authorization_status=not_granted_by_upload` distinctly; do not enable model execution merely because upload/index succeeded.
- Material selection is limited to versions uploaded into this case. The server checks reviewer role, case membership, same legal entity, source role, relation, purpose, grant expiry, and current permission. A project-customer contract requires an explicit reviewer attestation that it belongs to the same project and legal entity. The system records the reviewer and case/time reference but does not query a project directory or contract system to independently verify the relationship; do not label it system-verified. Historical-contract search and other-case material selection are out of this slice.
- Snapshot preview/freeze includes only selected files uploaded to this case. It does not query real contract or financial systems; the UI must say so. Every selected source must be server-reported ready, including legal entity, file hash, current authorization, amount scope, and index checks, and at least one ready main contract is mandatory.
- Frozen input is an immutable server record. Re-check authorization and versions when freezing; display the new case version and manifest identifier. The advanced freeze action alone does not start a review; the main-contract action sequences freeze and explicit run creation. The bounded development `contract_review` candidate locator is not a full review. The optional downloaded Markdown file is a non-final summary of the current authorized run projection; it is not a legal/enterprise conclusion or a signing recommendation.
- `/runs/{runId}` reads only server-authorized run results. Candidate evidence loads the normalized parsed artifact on demand and verifies source hash, page, Unicode code-point offsets, exact quote and text hash before display. For DOCX, the parser and PageIndex both consume the same versioned canonical PDF produced at upload processing; the parsed artifact, immutable source version and frozen input bind the canonical PDF hash and renderer identity. After authorization, the evidence drawer may fetch that derivative PDF and must verify its SHA-256 against the parsed artifact before showing the cited page. Its page numbers belong to the recorded canonical rendering, not to an abstract Word pagination. PDF and canonical PDF previews use browser page navigation without claiming quote highlight. If current authorization is denied or any page/content identity cannot be verified, hide the excerpt and page view. No result or no candidate is evidence that the contract lacks a relevant clause.
- `/runs/{runId}` displays `slot_candidates` only from the authorized result projection. Candidate state and value are labeled as awaiting human verification; each citation action resolves only an `evidence_id` already present in that result and reuses the existing source-verification drawer. Amount-bearing source access remains a server decision: the result API rechecks current per-document text/amount grants against the frozen task scope before returning any derived values; the UI neither infers permission nor relies on client-side masking. Unknown slot/value shapes are not rendered as arbitrary JSON, and absent candidates never imply a missing contract clause. Candidate values remain separate from legal/enterprise judgments and signing decisions.
- The run summary download must fetch `/runs/{runId}/results` again immediately before creating a local Markdown file, so current authorization and result integrity are rechecked. The file keeps contract findings, signing-decision source references, every check status/summary, scope/data limitations, and unverified candidates in separate sections; it includes the non-final disclaimer and the frozen input/run identities. A denied or unavailable recheck creates no file. Reports over 4 MiB are rejected with an explicit message before creating a file. The file is user-local and has no server signature or approval status.
- `/tasks` renders only the current actor's open `fact_review` tasks returned by the server's membership and exact required-role filter. It shows the task label, required role, creation time, and link to the bound run; it does not render the internal reason code. The current task contract lacks the disputed fact and supporting evidence, therefore the route is intentionally read-only even though the backend can record `confirm_fact`. Add a decision action only after a detail contract exposes the exact fact/evidence context and binds the submitted version/idempotency key to that context.
- Grants are per actor and purpose: `contract_review` and `upstream_comparison` are independent. A primary contract may be authorized for each purpose separately; an attachment is limited to `contract_review`; a project-customer contract is limited to `upstream_comparison`. The optional amount checkbox is off by default and never inferred from document role. Require an explicit validity duration (1, 4, 8, or at most 24 hours). The table displays each purpose's text/amount scope and expiry; revocation removes all purpose grants for that document.
- Revocation removes all active text/amount grants for the selected document, increments case version, and can cancel bound in-progress runs. Require a reason and an app-owned danger confirmation before sending it.
- Never infer the current authorized amount scope from a prior modal draft. Display the server-returned per-actor authorization and amount state after every command.
- Disabled actions require an adjacent reason, not color alone.

## Async and resilience

- Reads are cancelable or request-ID guarded; older list/detail responses cannot overwrite newer route/query state.
- Upload is pessimistic and server-confirmed. Use a unique `Idempotency-Key` per queued file and reuse the same key for safe retry of that exact file. On uncertain completion, refetch the document catalog before retrying; do not claim cancellation or failure without evidence.
- Permission mutations reconcile against the refreshed server catalog on error. Within the mounted detail page, uncertain retries reuse the exact authorization body or the same revocation body and idempotency key; after a page reload, inspect the server-reported selection, amount scope, and expiry before starting a new command.
- Freeze is pessimistic and server-verified. A timeout keeps the same preview available for retry; do not create a second preview until the first freeze outcome is resolved. A `409` discards the stale preview and requires a new server check.
- Preview and freeze are purpose-specific. Upstream-comparison snapshots require both the selected main contract and a same-case customer contract with a recorded reviewer relation attestation and current `upstream_comparison` grant. The advanced freeze action is preparation only. The main-contract workflow explicitly creates a development review after freezing; upstream comparison remains preparation only.
- Do not persist file bytes, bearer tokens, or sensitive document text in local/session storage, URLs, logs, or analytics.
- No offline queue. Offline mutations remain local only while still in the page and are not represented as submitted.
- A 401 does not silently discard selected files; a route-level remount may clear file bytes for privacy and must say so.

## Validation and permission

- Subject confirmation and administrator correction forms use `noValidate`, visible labels, inline errors, and field association through Ant Design Form; validate on submit, then on change for fields already in error. Correction uses a separate impact-review confirmation step and a stable idempotency key for uncertain retries.
- Client checks are advisory; server controls accepted media, size (30 MiB maximum), parser outcome, membership, tenant, and idempotency.
- The accepted upload roles are `primary_contract`, `attachment`, and `customer_contract`; a user must choose the role before upload. Each response separately reports document/index/selection/authorization state.
- Identity comes only from the server’s trusted auth context. In local development only, Vite’s server-side proxy may attach the configured dev token. The browser never stores or selects tenant/actor identity. Development auth is not OIDC and must not be enabled in shared/production environments.
- Case creation starts with an unconfirmed entity. Uploading the first main contract precedes subject confirmation; required confirmation is collected at review start or through the existing advanced form.
- The tenant entity-admin correction queue is separate from member-only case detail. It may reveal only case name/ID, current entity UUID, and version; it never reads or grants access to contract materials, results, source history, or ordinary case details.

## Verification

- Required: Web lint, typecheck, unit/component tests, production build; backend OpenAPI route/shape tests and PostgreSQL integration tests.
- Browser: list/detail/upload success, empty, no-results, 401, 403/404, server/network error, slow/stale reads, keyboard, narrow viewport, and reduced motion. Run results additionally require queued/running/waiting/completed/failed states, permission denial, timeout/manual GET refresh, valid and invalid citations, and Unicode code-point offset verification.
- Human tasks additionally require open/empty/error states, cursor append, authorization loss clearing previously rendered task metadata, route navigation to the bound run, and the read-only decision boundary until fact/evidence detail exists.
- Run history additionally requires authorized rows, empty/error/retry states, cursor append, clearing on authorization loss or case switch, narrow-screen overflow containment, and a separate, explicit main-contract start action.
- Evidence preview additionally requires verified text before offering PDF page views, strict MIME and size validation, current permission checks, URL cleanup on close/switch/navigation, canonical DOCX PDF hash verification and renderer identity, and truthful disclosure that DOCX page numbers refer to the frozen rendering rather than Word-native layout.
- Upload acceptance beyond synthetic/local samples and real OIDC sign-in are environment/user verification gates; do not claim those from component tests.
